# 데이터 흐름

**목적**: 현재 구조화 운영 데이터의 흐름과 앞으로 카메라 영상이 화면에 닿을 때의
서비스 경계를 구분한다.
**대상 독자**: 파이프라인 상의 서비스를 구현·수정하는 팀원과 AI 에이전트.

> 구조화된 직원·면담·강의실·알림 흐름은 `fastapi`에 구현돼 있다. 아래 영상 수집·추론
> 흐름은 초기 가정이며, 단계 사이 통신 방식은 결정되지 않았다.

## 현재 구현 흐름

```text
브라우저
→ fastapi 라우터
→ 도메인 서비스
→ 저장소 포트
→ memory 또는 MongoDB adapter
→ API 응답 또는 Jinja2 화면
```

직원 상태 관측과 좌석 관측은 `MOCK_INPUTS_ENABLED`인 local/dev에서만 사람이 구조화 값으로
입력한다. 운영 제품 탐색에는 입력 도구가 없다. 합성 영상 데모는 별도 고정 catalog를 읽을 뿐
직원·좌석 상태를 만들거나 저장하지 않는다.

| 쓰기 | 저장·파생 결과 | 화면 소비자 |
| --- | --- | --- |
| 사용자·직원 관리 | 사용자, 직원 프로필, 계정 연결, 감사 기록 | ADMIN 사용자·직원 관리 |
| 직원 상태 변경·평가 | 현재 상태와 append-only 이력 | 로그인 사용자 직원 조회 |
| 학생 면담 신청·상태 전이 | 면담 대기와 이력, 준비 알림 | 요청 학생, 연결된 STAFF |
| 강의실·일정·좌석 관리 | 강의실, 담당 STAFF, 일정, 좌석 | 로그인 사용자 좌석 조회 |
| 좌석 점유 전이 | 점유 이력, 마감 후 경고, 수신자별 알림 | 담당 STAFF와 ADMIN |

GET 요청은 시간 정책이나 상태 전이를 실행하지 않는다. 시간 기반 평가는 명시적인 쓰기 요청
또는 관련 상태 변경에서만 수행한다.

## 예정 영상 흐름

```text
카메라 또는 Jetson
→ 스트림 서버
→ 추론 서비스
→ FastAPI
→ 데이터 저장소
→ fastapi 화면
```

## 단계별 데이터 변환

| 단계 | 입력 | 출력 | 담당 |
| --- | --- | --- | --- |
| 1. 수집 | 카메라 영상 스트림 | 연속 프레임 | worker |
| 2. 샘플링 | 연속 프레임 | 추론 대상 프레임(일부) | worker |
| 3. 추론 | 프레임 | 탐지 결과(객체·좌표·신뢰도) | deeplearning |
| 4. 해석 | 탐지 결과 | 업무 의미가 부여된 이벤트 | fastapi |
| 5. 저장 | 이벤트 | 저장된 레코드 | fastapi |
| 6. 조회 | 조회 요청 | 응답 데이터 | fastapi |
| 7. 표시 | 응답 데이터 | Jinja2 렌더링 화면 | fastapi |

각 단계에서 지켜야 할 경계는 다음과 같다.

- **2단계에서 모든 프레임을 추론에 보내지 않는다.** 샘플링 없이 전량을 보내면
  추론 서비스가 병목이 된다. 샘플링 주기는 설정값으로 둔다.
- **3단계는 의미를 부여하지 않는다.** `person 1, conf 0.87`까지가 출력이다.
- **4단계에서 처음으로 업무 의미가 생긴다.** "재실 중", "이상 감지" 같은 판단은
  여기서만 이루어진다. 판단 기준(임계값, 지속 시간)은 설정으로 관리한다.

## 데이터 종류와 취급

| 데이터 | 성격 | 취급 |
| --- | --- | --- |
| 영상 프레임 | 대용량, 개인정보 포함 | 파이프라인 통과 중에만 존재. 보관 시 MinIO를 쓰되 **저장 범위 결정 필요** |
| 탐지 결과 | 소량, 구조화 | 계약 확정 후 업무 metadata로 변환 (`예정`) |
| 운영 metadata | 소량, 조회 대상 | 현재 v2 도메인은 MongoDB 저장 구현됨 |
| 지표 | 집계값 | monitoring이 수집. 개인 식별 정보를 label에 넣지 않는다 |

영상과 이벤트는 보존 기간과 접근 권한이 다르므로 저장 책임을 분리한다.
자세한 배경은 [아키텍처 개요](./overview.md#영상과-메타데이터의-저장-책임-분리)에 있다.

## 아직 결정되지 않은 것

이 흐름을 구현할 때 마주치게 될 미결정 항목이다.
확정 전까지 특정 방식에 강하게 결합된 코드를 굳히지 않는다.

| 지점 | 선택지 | 고려 사항 |
| --- | --- | --- |
| 1→2 수신 프로토콜 | RTSP / WebRTC / HTTP 푸시 | 실제 장비 사양 확인 필요 |
| 2→3 프레임 전달 | 동기 호출 / 공유 저장소 / 큐 | 지연과 유실 허용치에 따라 다름 |
| 3→4 결과 전달 | 동기 응답 / 큐 | 추론 지연이 API 응답을 막지 않아야 함 |
| 6→7 갱신 방식 | 폴링 / WebSocket / SSE | 필요한 실시간성 수준 미정 |
| 5 영상 저장 주체 | worker / fastapi | 저장 범위 합의 후 결정 |

## 실패 시 동작

각 단계는 다음 단계가 멈춰도 전체가 무너지지 않게 설계한다.
구체적인 정책은 **결정 필요**이며, 아래는 설계 시 답해야 할 질문이다.

- 추론 서비스가 응답하지 않으면 프레임을 버리는가, 쌓아두는가?
- 저장소 장애 시 이벤트를 잃는가, 재시도하는가?
- 카메라 연결이 끊긴 동안의 공백을 화면에 어떻게 표시하는가?

세 질문 모두 "쌓아둔다"를 고르면 메모리 한계를 함께 정해야 한다.
답을 정하면 이 절을 갱신하고 ADR로 남긴다.
