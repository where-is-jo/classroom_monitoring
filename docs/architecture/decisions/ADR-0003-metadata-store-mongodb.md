# ADR-0003: 메타데이터 저장소로 MongoDB 채택

## Status

Accepted

## Context

탐지 이벤트, 카메라 설정, 사용자 정보를 보관할 저장소를 정해야 한다.
[아키텍처 개요](../overview.md)에서 MongoDB를 후보로 두고 미결정 상태였다.

저장할 데이터의 성격은 다음과 같다.

- **탐지 이벤트** — 계속 쌓이는 시계열성 기록. 건수가 가장 많다.
  모델이 바뀌면 탐지 결과에 담기는 필드가 달라질 수 있다.
- **카메라 설정** — 소량. 카메라마다 필요한 설정 항목이 다를 수 있다.
- **사용자·권한** — 소량. 권한 모델은 아직 **결정 필요** 상태다.

제약은 두 가지다. 첫째, 스키마가 확정되지 않았다. 모델과 탐지 결과 형식이 정해지지 않아
이벤트 레코드의 필드가 초기에 자주 바뀔 가능성이 크다.
둘째, 저장소 운영 경험이 팀에 많지 않다.

저장소는 되돌리는 비용이 크므로 결정을 기록한다.

## Decision

**메타데이터 저장소로 MongoDB를 사용한다.**

- 탐지 이벤트, 카메라 설정, 사용자 정보를 MongoDB에 보관한다.
- 영상과 스냅샷 같은 바이너리는 여기에 넣지 않는다. [ADR-0004](./ADR-0004-object-storage-minio.md)를 따른다.
- backend는 MongoDB에 직접 접근하지 않고 [ADR-0002](./ADR-0002-backend-layered-with-ports.md)의
  저장소 포트를 통해 접근한다. MongoDB 관련 코드는 어댑터에만 둔다.
- 접속 정보는 `DATABASE_URL` 환경변수로 주입한다. 값을 저장소에 두지 않는다.

**스키마가 유연하다는 것이 검증을 생략해도 된다는 뜻은 아니다.**
저장 전 검증은 애플리케이션 계층에서 수행한다. 컬렉션 구조와 인덱스는 조회 패턴이
드러나는 대로 문서에 남긴다.

## Alternatives Considered

### 대안 A: PostgreSQL

- 장점: 스키마 제약과 트랜잭션이 강하다. 관계형 조회가 필요할 때 유리하다.
  운영 자료와 참고 사례가 많다.
- 단점: 탐지 결과 필드가 자주 바뀌는 초기 단계에서 마이그레이션 부담이 크다.
  모델 교체마다 스키마 변경이 따라온다.
- 채택하지 않은 이유: 현재 필요한 조회가 "기간·카메라별 이벤트 목록" 수준이라
  관계형의 강점을 쓸 일이 적다. 반대로 스키마 변경 빈도는 높을 것으로 예상된다.

### 대안 B: 시계열 전용 저장소 (InfluxDB 등)

- 장점: 탐지 이벤트 같은 시계열 데이터의 저장·집계에 최적화되어 있다.
- 단점: 카메라 설정과 사용자 정보는 시계열이 아니어서 저장소를 하나 더 두게 된다.
  팀에 운영 경험이 없다.
- 채택하지 않은 이유: 저장소를 둘로 나눌 만큼 데이터 규모가 크지 않다.
  집계 성능이 문제가 되면 그때 별도 ADR로 도입한다.

## Consequences

**얻는 것**

- 탐지 결과 필드가 바뀌어도 마이그레이션 없이 흡수할 수 있다.
- 모델 교체로 인한 스키마 변경이 배포를 막지 않는다.
- 카메라마다 다른 설정 항목을 하나의 컬렉션에서 다룰 수 있다.

**감수하는 것**

- 스키마 제약이 없으므로 **애플리케이션이 검증 책임을 진다.** 검증을 빠뜨리면
  형식이 뒤섞인 레코드가 쌓이고 나중에 정리 비용이 든다.
- 여러 컬렉션에 걸친 원자적 갱신이 관계형보다 다루기 까다롭다.
  트랜잭션이 필요한 흐름이 생기면 설계를 재검토한다.
- 조회 패턴이 굳기 전에는 인덱스를 최적화하기 어렵다. 이벤트가 쌓이면
  조회 성능을 다시 확인해야 한다.
