# ADR-0002: backend 계층형 구조와 경계 포트

## Status

Accepted

## Context

`webapps/backend` 구현을 시작하기 전에 내부 구조를 정해야 한다.

두 가지 제약이 맞선다.

**팀 숙련도** — 헥사고날 아키텍처 경험자가 팀에 없다. 도메인 모델 순수성, 인바운드·아웃바운드
포트, 계층 간 매핑 객체를 모두 갖추면 엔드포인트 하나를 추가할 때 파일 6~8개를 만들게 된다.
규칙을 지키지 못하면 구조만 남고 이점은 사라진다.

**외부 기술 미확정** — 반대로 인터페이스 없이 구현체를 직접 호출하면, 나중에 저장소나 통신
방식이 바뀔 때 서비스 계층과 테스트를 함께 고쳐야 한다. 이 시점에 추론 서비스 통신 방식과
알림 채널이 결정되지 않았다.

핵심 판단은 **이 프로젝트의 도메인이 얇다**는 것이다. 다루는 개념은 탐지 이벤트, 카메라,
사용자 정도이며 복잡한 도메인 규칙이 없다. 헥사고날이 해결하는 문제(도메인 로직이 인프라에
오염되는 것)는 여기서 크지 않고, 실제 위험은 **외부 시스템과 닿는 지점**에 몰려 있다.

따라서 그 경계에만 포트를 두고 나머지는 계층형을 유지한다.

기존 [backend-agent 규칙](../../agents/backend-agent.md)은 이미 "서비스 계층은 FastAPI에
의존하지 않는다"를 요구하고 있다. 이 결정은 그 요구를 형식화하는 것이며 새 제약을 더하지 않는다.

## Decision

### 1. 계층 구조

```text
router  →  service  →  port (Protocol)  ←  adapter
 HTTP      비즈니스 로직    인터페이스        구현체
```

- `router`는 HTTP 관심사만 다룬다. FastAPI에 의존해도 된다.
- `service`는 비즈니스 로직을 담고 **포트에만 의존**한다. 어댑터를 직접 import하지 않는다.
- `adapter`는 실제 기술(MongoDB, MinIO, HTTP 클라이언트)로 포트를 구현한다.
- 어댑터를 서비스에 연결하는 조립 코드는 `shared/`에 한 곳으로 모은다.

### 2. 포트는 프로세스 외부 I/O 경계 4곳에만 정의한다

| 포트 | 대상 | 구현체 |
| --- | --- | --- |
| `EventRepository` 등 저장소 포트 | 메타데이터 저장소 | MongoDB ([ADR-0003](./ADR-0003-metadata-store-mongodb.md)) |
| `InferenceClient` | 추론 서비스 호출 | 통신 방식 **결정 필요** |
| `ObjectStorage` | 영상·스냅샷 보관 | MinIO ([ADR-0004](./ADR-0004-object-storage-minio.md)) |
| `Notifier` | 알림 발송 | 채널 **결정 필요** |

**포트를 만드는 기준은 "프로세스 밖으로 나가는 I/O인가"다.**

MongoDB와 MinIO는 확정됐지만 포트를 유지한다. 이유는 기술 교체 대비가 아니라
**단위 테스트에서 실제 DB와 객체 저장소 없이 서비스 로직을 검증하기 위해서**다.
MinIO는 S3 호환이므로 실제 S3로 옮길 가능성도 남아 있다.

다음에는 포트를 만들지 않는다.

- 같은 프로세스 안의 서비스 간 호출
- 순수 계산 로직, 값 변환
- 표준 라이브러리와 확정된 유틸리티

새 포트를 추가하려면 **"이것이 프로세스 밖과 통신하는가"에 예라고 답할 수 있어야 한다.**
이 기준을 지키지 않으면 6개월 뒤 포트가 20개가 된다.

### 3. `ABC`가 아니라 `typing.Protocol`을 쓴다

구현체가 상속을 강제받지 않아 어댑터를 독립적으로 작성할 수 있고, 테스트 대역을
별도 상속 없이 만들 수 있다. 런타임 검사가 필요한 경우에만 `@runtime_checkable`을 붙인다.

### 4. 기능(도메인)별 디렉터리로 나눈다

기술 계층별(`routers/`, `services/`)이 아니라 기능별(`events/`, `cameras/`)로 나눈다.
기능 하나를 추가·삭제·리뷰할 때 디렉터리 하나만 보면 된다.

구체적인 디렉터리 구조는 [backend README의 디렉터리 구조](../../../webapps/backend/README.md#디렉터리-구조)에 있다.
여기에 같은 트리를 복사하지 않는다.

### 5. 도메인 모델과 스키마를 구분한다

- 도메인 모델은 평범한 `dataclass`로 둔다. 서비스 계층과 포트가 주고받는 타입이다.
- Pydantic 스키마는 **경계에만** 둔다. HTTP 요청·응답 검증용이며 서비스 계층으로 넘기지 않는다.
- 계층마다 매핑 객체를 만들지 않는다. 매핑은 router와 adapter 두 곳에서만 일어난다.

## Alternatives Considered

### 대안 A: 완전 헥사고날 아키텍처

`domain/` · `application/ports/in`·`out` · `application/usecases/` · `adapters/in`·`out`으로
나누고 계층마다 매핑 객체를 둔다.

- 장점: 도메인 분리가 가장 명확하다. 도메인 규칙이 복잡해져도 구조가 버틴다.
- 단점: 팀에 경험자가 없어 학습 비용이 크다. 도메인이 얇은 상태에서 매핑 계층
  (Entity ↔ DTO ↔ Schema)이 이득보다 비용이 크다. 엔드포인트 하나에 파일 6~8개가 생긴다.
- 채택하지 않은 이유: 해결하려는 문제(복잡한 도메인 규칙의 오염)가 이 프로젝트에 아직 없다.
  구조를 먼저 갖추고 도메인이 따라오기를 기대하는 것은 순서가 뒤바뀐 선택이다.
  도메인이 실제로 복잡해지면 그때 새 ADR로 전환할 수 있다.

### 대안 B: 순수 계층형 (인터페이스 없음)

`router → service → repository` 구조에서 서비스가 구현체를 직접 호출한다.

- 장점: 새로 배울 것이 사실상 없다. 파일 수가 가장 적다.
- 단점: 서비스 계층 단위 테스트에 실제 MongoDB 또는 mock 라이브러리가 필요하다.
  추론 통신 방식과 알림 채널이 미확정인 상태에서 구현체를 직접 참조하면
  결정이 내려질 때 서비스 계층까지 수정 범위가 번진다.
- 채택하지 않은 이유: 포트 4개를 만드는 비용보다 테스트에서 잃는 비용이 크다.

## Consequences

**얻는 것**

- 서비스 계층 단위 테스트에 실제 DB·객체 저장소가 필요 없다. 테스트 대역으로 대체한다.
- 추론 통신 방식과 알림 채널 결정을 어댑터 교체로 흡수할 수 있다.
- 새로 배울 개념이 `typing.Protocol`과 의존성 주입 두 가지로 한정된다.
- 기능별 디렉터리라 변경 범위가 리뷰에서 한눈에 보인다.

**감수하는 것**

- 포트 4개만큼 간접 계층이 생긴다. 코드를 따라갈 때 한 단계를 더 거친다.
- "포트를 만들어야 하나"라는 판단이 매번 필요하다. 위 기준으로 줄였지만 없어지지는 않는다.
- 기능별 분할은 FastAPI 튜토리얼 다수가 쓰는 계층별 구조와 달라, 예제를 그대로 옮길 수 없다.
- 도메인이 복잡해지면 이 구조로 부족해질 수 있다. 그 시점에 새 ADR이 필요하다.
