# 결정 기록

**목적**: 되돌리기 어려운 기술 결정을 그 배경과 함께 한 파일에 쌓는다.
**대상 독자**: 나중에 "왜 이렇게 했지?"를 묻게 될 팀원과 AI 에이전트.

코드는 결정의 결과만 보여 준다. 왜 다른 방법을 쓰지 않았는지는 남지 않는다.
그래서 몇 달 뒤에 같은 논의를 반복하거나, 이유가 있어서 피했던 방법을 다시 시도하게 된다.
이 파일은 그 반복을 막기 위한 기록이다.

> **번호를 0001부터 다시 매겼다.** 프로젝트 주제가 사무실 직원 재석·통화 모니터링에서
> 강의실 학생 출결·좌석 모니터링으로 바뀌면서, 이전 번호 체계(0002~0009)의 결정을
> 폐기하고 새 주제 기준으로 다시 정했다. 주제와 무관하게 유효한 결정(계층 구조, 설계
> 패턴, 저장소, 워커 분리, 프레임 버퍼)은 새 번호로 다시 서술했다. 이전 번호로 쓴
> 문서·커밋을 만나면 이 파일의 목록과 대조한다. 과거 본문은 Git 이력에만 남는다.

## 언제 기록하는가

다음 중 하나에 해당하면 항목을 추가한다.

- 되돌리는 비용이 큰 선택 — 저장소, 통신 방식, 프레임워크, 프로토콜
- 여러 서비스의 구조에 영향을 주는 결정
- [Architecture Rules](../agents/AGENTS.md#architecture-rules)의 예외를 두는 결정
- [미결정 항목](./README.md#미결정-항목)을 확정한 경우

다음은 기록하지 않는다. 라이브러리 버전 갱신, 되돌리기 쉬운 구현 방식 선택,
코딩 스타일([코딩 규칙](../conventions/coding-convention.md)에 둔다).

## 어떻게 기록하는가

**결정마다 파일을 만들지 않는다.** 이 파일 맨 아래에 항목 하나를 추가한다.

1. 번호는 4자리로 순차 증가시킨다. 비어 있는 번호를 재사용하지 않는다.
2. 아래 뼈대를 채운다. **대안을 비우지 않는다.** 대안을 적을 수 없다면
   아직 결정할 만큼 검토되지 않은 것이다.
3. 영향받는 문서([아키텍처](./README.md)의 미결정 항목 표, 서비스 README,
   [루트 README](../../README.md))를 함께 갱신한다.

```markdown
## NNNN · <결정 요약>

**상태**: 확정 | 대체됨(NNNN) | 폐기

**배경**: 결정을 미룰 수 없게 만든 상황.

**결정**: 무엇을 하기로 했는지. "검토한다"가 아니라 확정된 행동으로 쓴다.

**대안**: 검토한 선택지와 채택하지 않은 이유.

**결과**: 얻는 것과 감수하는 것을 모두 적는다.

**남은 일**: 이 결정을 반영하려면 아직 해야 할 것.
```

**확정된 항목의 내용은 사후에 고치지 않는다.** 결정이 바뀌면 새 번호로 항목을 추가하고,
이전 항목의 상태만 `대체됨(NNNN)`으로 바꾼다. 과거 기록을 고치면 "그때 무엇을
알고 있었는가"가 사라진다. 오타나 링크 수정은 예외다.

## 0001 · fastapi 계층형 구조와 경계 포트

**상태**: 확정

**배경**: `webapps/fastapi` 구현 전에 내부 구조를 정해야 했다. 팀에 헥사고날 아키텍처
경험자가 없어 완전한 형태를 갖추면 엔드포인트 하나에 파일 6~8개가 생긴다. 반대로
인터페이스 없이 구현체를 직접 호출하면 저장소나 통신 방식이 바뀔 때 서비스 계층과
테스트를 함께 고쳐야 한다. 핵심 판단은 **이 프로젝트의 도메인이 얇다**는 것이었다.
헥사고날이 해결하는 문제(도메인 로직이 인프라에 오염되는 것)는 여기서 크지 않고,
실제 위험은 **외부 시스템과 닿는 지점**에 몰려 있다.

**결정**: 그 경계에만 포트를 두고 나머지는 계층형을 유지한다.

1. **호출 방향은 `router → service → port ← adapter`다.**
   - `router`는 HTTP 관심사만 다룬다. FastAPI에 의존해도 된다.
   - `service`는 비즈니스 로직을 담고 **포트에만 의존**한다. 어댑터를 직접 import하지 않는다.
   - `adapter`는 실제 기술(MongoDB, MinIO, HTTP 클라이언트)로 포트를 구현한다.
   - 조립 코드는 `app/shared/dependencies.py` 한 곳에 모은다. 주입은 FastAPI `Depends`를
     쓰고 별도 컨테이너를 두지 않는다.
2. **포트는 프로세스 외부 I/O 경계 4곳에만 정의한다** — 저장소, 추론 클라이언트,
   객체 저장소, 알림. 판단 기준은 **"프로세스 밖으로 나가는 I/O인가"** 하나다.
   같은 프로세스 안의 서비스 호출, 순수 계산, 확정된 라이브러리에는 만들지 않는다.
   MongoDB와 MinIO가 확정된 뒤에도 포트를 유지하는 이유는 기술 교체 대비가 아니라
   **단위 테스트에서 실제 DB 없이 서비스 로직을 검증하기 위해서**다.
3. **`ABC`가 아니라 `typing.Protocol`을 쓴다.** 구현체가 상속을 강제받지 않아
   테스트 대역을 별도 상속 없이 만들 수 있다.
4. **기술 계층별이 아니라 기능(도메인)별 디렉터리로 나눈다.** 기능 하나를
   추가·삭제·리뷰할 때 디렉터리 하나만 보면 된다.
5. **도메인 모델과 스키마를 구분한다.** 도메인 모델은 `dataclass`, Pydantic 스키마는
   HTTP 경계에만 둔다. 매핑은 router와 adapter 두 곳에서만 일어난다.

**대안**:

- *완전 헥사고날* — 도메인 분리가 가장 명확하지만, 해결하려는 문제(복잡한 도메인 규칙의
  오염)가 이 프로젝트에 아직 없다. 구조를 먼저 갖추고 도메인이 따라오기를 기대하는 것은
  순서가 뒤바뀐 선택이다. 도메인이 실제로 복잡해지면 그때 새 항목으로 전환한다.
- *순수 계층형(인터페이스 없음)* — 배울 것이 가장 적지만, 서비스 계층 단위 테스트에
  실제 MongoDB나 mock 라이브러리가 필요하다. 포트 4개를 만드는 비용보다 테스트에서
  잃는 비용이 크다.

**결과**: 서비스 계층 테스트에 실제 DB가 필요 없고, 통신 방식 결정을 어댑터 교체로
흡수할 수 있다. 새로 배울 개념은 `typing.Protocol`과 의존성 주입 둘뿐이다.
대신 포트 4개만큼 간접 계층이 생기고, "포트를 만들어야 하나"라는 판단이 매번 필요하다.
기능별 분할은 FastAPI 튜토리얼 다수의 계층별 구조와 달라 예제를 그대로 옮길 수 없다.

**남은 일**: 학생 상태 판정 규칙([0008](#0008--학생-상태-판정을-rule-engine으로-분리하고-fastapi가-소유한다))이
들어오면 도메인이 두꺼워진다. 그 시점에 이 구조가 여전히 맞는지 재검토한다.

## 0002 · 설계 패턴 적용 범위와 판단 기준

**상태**: 확정

**배경**: [0001](#0001--fastapi-계층형-구조와-경계-포트)이 계층 구조를 정했지만, 그 계층
**안에서** 어떤 패턴을 언제 쓰는지는 정하지 않았다. 두 가지가 이 결정을 앞당겼다.

첫째, **코드의 상당 부분을 AI 에이전트가 생성한다.** AI는 패턴을 교과서적으로 정확하게,
그리고 **과하게** 만든다. 지시하지 않아도 인터페이스와 팩토리와 디스패처를 붙인다.
이 프로젝트의 위험은 패턴이 부족한 것이 아니라 **필요해지기 전에 추상화가 먼저
들어오는 것**이다.

둘째, **거론된 패턴 중 절반은 이미 있다.** 저장소 포트가 Repository이고,
`app/shared/dependencies.py`가 Composition Root이며, 각 `service.py`는 라우터에 대해
이미 파사드로 동작한다. 이들을 "새로 도입"하면 같은 것에 이름이 두 개 생긴다.

**결정**: **설계 패턴은 아래 표에 있는 것만, 표에 적힌 조건을 모두 만족할 때만 만든다.**
어휘는 기존의 포트·어댑터·서비스·조립을 그대로 쓰고, GoF 이름은 이 항목에서만 쓴다.

| 패턴 | 만들어도 되는 조건 (전부 예여야 함) |
| --- | --- |
| 포트 | 프로세스 밖으로 나가는 I/O인가 |
| Repository | 포트 기준과 같다. 별도 기준을 두지 않는다 |
| Facade | 두 개 이상의 **기능 디렉터리**를 가로지르는가 + 화면과 API가 그 조합을 함께 쓰는가 |
| Strategy | 변형이 2개 이상 **실재**하는가 + 선택이 설정·런타임 값으로 이뤄지는가 + 각 변형이 독립된 의존성이나 상태를 갖는가 |
| Observer | 한 도메인 이벤트에 **서로를 모르는 반응이 3개 이상** 붙는가 + 반응이 실패해도 원래 작업을 되돌리지 않아도 되는가 + 실행 순서가 결과에 영향을 주지 않는가 |

"실재한다"는 것은 **지금 코드에 있다**는 뜻이다. 앞으로 생길 것 같다는 예상은 조건을
만족시키지 못한다. 그 예상이 맞는 경우보다 틀리는 경우가 많고, 틀렸을 때 남는 추상화는
지우는 사람이 없다.

- **Facade는 새 파일 종류를 만들지 않는다.** 한 기능 안에서는 `service.py`가 이미
  파사드다. 여러 기능을 조합하는 기능이 생기면 **그 기능의 `service.py`가 파사드가 된다.**
  `facade.py` 같은 파일을 만들지 않는다.
- **Strategy는 분기를 없애려고 만들지 않는다.** `if` 세 줄을 클래스 세 개로 바꾸는 것은
  읽을 파일이 늘어나는 것이다. 값을 하는 지점은 **변형마다 딸린 의존성과 상태가 다른
  곳**이다. 그전까지 판단 로직은 순수 함수로 둔다. **학생 상태 판정 규칙을 상태별
  클래스로 나누는 것도 여기에 해당한다** — 규칙은 순수 함수로 시작한다.
- **Observer는 도입을 보류한다.** 제어 흐름을 코드에서 지워, "이 함수를 실행하면 무슨
  일이 일어나는가"를 호출 지점에서 읽을 수 없게 된다. 게다가 서비스 간 통신 방식이
  미정이라 지금 인프로세스 이벤트를 만들면 나중에 경로가 두 개가 된다. 트리거 전까지는
  서비스 메서드 안에서 순서대로 명시적으로 호출한다.
- **표에 없는 패턴(Factory, Singleton, Decorator 등)은 코드에 넣지 않는다.**
  쓰려면 이 표에 행을 추가하는 결정을 먼저 기록한다.

**대안**:

- *Facade와 Strategy를 지금 도입* — 기능이 몇 개뿐인 지금 파사드는 얇은 위임 껍데기가
  되고 Strategy는 구현체가 하나뿐인 인터페이스가 된다. 0001이 완전 헥사고날을 기각한
  논리와 같다.
- *문서화하지 않고 코드 리뷰에서 판단* — AI 에이전트는 매번 다르게 생성하고 리뷰어마다
  기준이 갈린다. 더 큰 문제는 시점이다. 리뷰 시점에는 이미 코드가 쓰여 있어 "동작은
  하니까"로 통과하기 쉽다. 이 결정의 목적은 **쓰기 전에 안 쓰기로 결정하게 만드는 것**이다.
- *GoF 이름을 1급 어휘로 채택* — 저장소 전체가 포트·어댑터 어휘로 서술되어 있어
  같은 것을 두 이름으로 부르는 구간이 생긴다.

**결과**: AI 에이전트에게 줄 수 있는 명확한 문장이 생긴다 — "판정 질문에 전부 예라고
답할 수 없으면 만들지 않는다." 지시가 없을 때의 기본 동작이 "만들지 않는다"가 된다.
대신 트리거에 도달하면 그때 리팩터링이 필요하고, 그 시점까지 비슷한 코드가 두 벌
존재하는 기간이 생긴다.

**남은 일**: Facade·Strategy·Observer 각각의 트리거에 도달하면 새 항목을 기록한다.
상태 판정 규칙이 상태별로 독립된 의존성을 갖게 되면 Strategy 조건을 다시 본다.
Observer는 서비스 간 통신 방식 결정과 함께 다룬다.

## 0003 · 메타데이터 저장소로 MongoDB 채택

**상태**: 확정

**배경**: 학생 원장, 좌석 배치, 얼굴 프로필 메타데이터, 탐지 이벤트, 상태 이력을
보관할 저장소를 정해야 했다. 스키마가 확정되지 않았고 — 사용할 모델과 탐지 결과
형식이 정해지지 않아 레코드 필드가 초기에 자주 바뀔 가능성이 크다 — 팀에 저장소
운영 경험이 많지 않았다.

**결정**: **메타데이터 저장소로 MongoDB를 사용한다.**

- 학생, 강의실·좌석, 좌석 지정, 얼굴 프로필 메타데이터, 탐지 이벤트, 학생 상태 이력,
  수업 세션을 MongoDB에 보관한다.
- 영상, 스냅샷, 얼굴 원본 이미지 같은 바이너리는 넣지 않는다.
  [0004](#0004--영상과-얼굴-이미지-저장소로-minio-채택)를 따른다.
- fastapi는 MongoDB에 직접 접근하지 않고 [0001](#0001--fastapi-계층형-구조와-경계-포트)의
  저장소 포트를 통한다. MongoDB 관련 코드는 어댑터에만 둔다.
- 접속 정보는 `DATABASE_URL` 환경변수로 주입한다.

**스키마가 유연하다는 것이 검증을 생략해도 된다는 뜻은 아니다.**
저장 전 검증은 애플리케이션 계층에서 수행한다.

**얼굴 embedding을 어디에 둘지는 이 항목이 정하지 않는다.** 벡터 검색이 필요해지면
MongoDB 안에 둘지 별도 벡터 저장소를 둘지 다시 정한다. MVP의 등록 인원 규모에서는
전수 비교로 충분하다고 보고 저장소를 늘리지 않는다.

**대안**:

- *PostgreSQL* — 스키마 제약과 트랜잭션이 강하지만, 탐지 결과 필드가 자주 바뀌는
  초기 단계에서 마이그레이션 부담이 크다. 현재 필요한 조회가 "기간·강의실·학생별 목록"
  수준이라 관계형의 강점을 쓸 일이 적다.
- *시계열 전용 저장소(InfluxDB 등)* — 탐지 이벤트에는 맞지만 학생 원장·좌석 배치는
  시계열이 아니어서 저장소를 하나 더 두게 된다. 저장소를 나눌 만큼 데이터 규모가 크지 않다.

**결과**: 탐지 결과 필드가 바뀌어도 마이그레이션 없이 흡수한다. 대신 **애플리케이션이
검증 책임을 진다.** 여러 컬렉션에 걸친 원자적 갱신이 관계형보다 까다롭고,
조회 패턴이 굳기 전에는 인덱스를 최적화하기 어렵다.

**남은 일**: 컬렉션 구조와 인덱스를 조회 패턴 확정 후 문서화한다. 탐지 이벤트·상태
이력의 보존 기간 정책은 아직 `결정 필요`다. 얼굴 관련 컬렉션의 접근 권한 분리 방식도
개인정보 합의와 함께 정한다.

## 0004 · 영상과 얼굴 이미지 저장소로 MinIO 채택

**상태**: 확정

**배경**: 영상과 얼굴 이미지는 메타데이터와 성격이 완전히 다르다. 크기가 파일당
수 MB~GB이고, 녹화 시간에 비례해 늘어나며, **미성년일 수 있는 학생의 얼굴이 그대로
담긴다.** 두 데이터를 한 저장소에 넣으면 백업 주기, 보존 기간, 접근 권한을 분리할 수 없다.

**결정**: **영상, 스냅샷, 얼굴 등록 이미지를 MinIO에 보관한다.**

- 바이너리는 MinIO 버킷에 두고, 메타데이터 저장소에는 **참조(버킷·객체 키)만** 기록한다.
- fastapi는 `ObjectStorage` 포트를 통해 접근한다. MinIO SDK는 어댑터에만 둔다.
- **영상 버킷과 얼굴 이미지 버킷을 나눈다.** 둘은 보존 기간과 열람 주체가 다르다.
  영상은 사건을 되짚는 용도이고, 얼굴 등록 이미지는 특정 학생에게 귀속되며 그
  학생의 요청으로 삭제할 수 있어야 한다.
- **S3 호환 API 범위 안에서 사용한다.** MinIO 고유 기능에 의존하지 않으면 나중에
  실제 S3나 다른 호환 저장소로 옮길 수 있다.

**MinIO를 쓰기로 한 것이지, 무엇을 얼마나 저장할지 정한 것이 아니다.**
아래는 기술 결정이 아니라 합의 사항이며, 정해지기 전에는 그 범위를 넓히는 기능을
만들지 않는다.

| 항목 | 상태 |
| --- | --- |
| 상시 녹화 여부(전체 저장 / 이벤트 구간만 / 스냅샷만) | 결정 필요 |
| 보존 기간과 자동 삭제 | 결정 필요 |
| 접근 권한 — 누가 영상과 얼굴 이미지를 열람할 수 있는가 | 결정 필요 |
| 얼굴 원본 이미지를 남길지, embedding만 남길지 | 결정 필요 |
| 개인정보 처리 근거, 동의 절차, 미성년자 처리 | 결정 필요 |

**대안**:

- *서버 로컬 파일 시스템* — 가장 단순하지만 인스턴스가 늘면 파일 위치가 갈리고
  보존 기간 자동화를 직접 구현해야 한다. 옮기는 비용이 처음부터 객체 저장소를 쓰는
  비용보다 크다.
- *퍼블릭 클라우드 객체 저장소(S3 등)* — 운영 부담이 없지만 학생 얼굴이 담긴 데이터를
  외부로 내보내는 것에 대한 합의가 없다. S3 호환 범위에서 쓰면 나중에 옮길 수 있다.
- *MongoDB GridFS* — 저장소를 하나로 유지할 수 있지만 백업·보존·권한을 분리할 수 없어
  저장 책임 분리 원칙에 정면으로 어긋난다.

**결과**: 영상·얼굴 이미지와 메타데이터의 보존 기간·접근 권한·백업 주기를 따로 정할 수
있고, 개인정보가 담긴 데이터의 접근 통제 지점이 명확해진다. 대신 운영할 구성 요소가
하나 늘고, 참조는 있는데 객체가 없는 상태를 다뤄야 한다.

**남은 일**: 위 표의 저장 정책 합의. 얼굴 이미지 버킷의 키 규칙과 삭제 절차 정의.
영상 버킷의 키 규칙은 [0007](#0007--recorder-worker의-저장-구조와-보존-정책)에서 정했다.

## 0005 · worker를 역할별 워커로 분리

**상태**: 확정

**배경**: `worker`는 단일 스크립트였다. USB 카메라 1대를 FFmpeg으로 RTSP에 올리고,
OpenCV로 받아, 영상과 프레임을 로컬에 저장하는 흐름 전체가 한 진입점의 최상위
코드에 있었다. 여기에 추론과 MinIO 적재를 더 붙여야 하는데 세 가지가 걸렸다.

첫째, **단계마다 멈추는 이유와 늘려야 할 자원이 다르다.** 수신은 네트워크와
카메라 연결에, 추론은 GPU에, 저장은 디스크와 객체 저장소 대역폭에 묶인다.
한 프로세스에 두면 추론이 느릴 때 프레임 수신이 함께 밀리고, 저장이 디스크를
붙들면 추론이 굶는다.

둘째, **카메라를 여러 대로 늘려야 한다.** MVP는 강의실 좌우 좌석 라인을 각각 맡는
카메라 2대로 시작하고, 정면 카메라와 교실 전체 카메라가 뒤따를 수 있다. 스크립트를
카메라 수만큼 띄우면 설정과 장애 지점이 그만큼 늘어난다.

셋째, **저장 범위가 아직 합의되지 않았다**([0004](#0004--영상과-얼굴-이미지-저장소로-minio-채택)).
저장 코드가 수신 경로에 섞여 있으면 "저장 범위를 넓히는 기능을 만들지 않는다"는 제약을
설정 하나로 지킬 수 없다.

**결정**: `worker`를 파이프라인 단계별 워커로 나눈다.

| 디렉터리 | 책임 |
| --- | --- |
| `worker/stream` | RTSP 수신, 연결 유지·재연결, 프레임 샘플링 |
| `worker/inference` | 프레임에 모델을 적용해 탐지 결과를 만드는 실행 단계 |
| `worker/recorder` | 영상 세그먼트를 객체 저장소에 적재 |

**상태 판정 워커를 두지 않는다.** 탐지 결과를 학생 상태로 바꾸는 일은 fastapi가
소유한다([0008](#0008--학생-상태-판정을-rule-engine으로-분리하고-fastapi가-소유한다)).

함께 확정하는 것은 다음 네 가지다.

1. **수신 프로토콜은 RTSP over TCP, 스트림 서버는 MediaMTX, 프레임 처리는 OpenCV다.**
   UDP는 패킷 손실로 H264 매크로블록이 깨졌다. 실측 대응 기록은
   [카메라 수집 구성](../../worker/stream/camera-guides.md)에 있다.
2. **카메라 대수만큼 프로세스를 띄우지 않는다.** 워커 애플리케이션 하나가
   소스마다 스레드를 들고 관리한다. OpenCV의 프레임 읽기는 GIL을 놓는 블로킹
   호출이라 스레드로 병행된다. 소스 목록은 `STREAM_SOURCES` 하나로 주입한다.
3. **`recorder`는 `stream`의 프레임을 받지 않고 MediaMTX에서 직접 받는다.**
   저장 때문에 추론 경로가 느려지지 않게 한다.
4. **`stream`의 로컬 저장은 개발용이며 기본값이 꺼져 있고 `APP_ENV=prod`에서는
   켤 수 없다.** 학습 데이터 확보용이며, 운영 저장은 `recorder`가 맡는다.

**대안**:

- *단일 워커 유지, 내부 모듈로만 분리* — 배포 단위가 하나여서 운영이 단순하다.
  하지만 GPU가 필요한 추론과 그렇지 않은 수신이 같은 프로세스에 묶여 자원을 따로
  줄 수 없고, 저장 코드를 수신 경로에서 떼어내지 못해 위 셋째 문제가 남는다.
- *카메라마다 워커 프로세스* — 한 카메라의 장애가 다른 카메라에 닿지 않아 격리가
  가장 확실하다. 대신 카메라를 늘릴 때마다 프로세스와 설정이 함께 늘고, 지금 필요한
  대수에서는 스레드 격리로 충분하다. 스레드로 감당이 안 되는 대수에 도달하면
  새 항목으로 다시 정한다.
- *메시지 큐로 워커 연결* — 단계 사이 결합이 가장 낮다. 그러나 단계 간 전달 방식
  자체가 아직 `결정 필요`라 지금 큐를 고르면 그 결정을 앞당겨 굳히게 된다.
  전달 방식은 분리와 별개로 남겨 둔다.

**결과**: 단계별로 배포와 자원 할당을 따로 정할 수 있고, 저장 기능을 설정 하나로
끌 수 있게 되어 개인정보 제약을 코드가 아니라 설정 검증으로 강제한다. 카메라 확장이
설정 변경으로 끝난다. 대신 운영할 프로세스가 늘고, 단계 사이 전달 방식이 확정되기
전까지 `stream` 이후 단계의 출력이 갈 곳이 없다.

**남은 일**: 탐지 결과를 fastapi로 넘기는 방식 확정. 저장 범위·보존 기간 합의.
실제 카메라 2대 이상에서의 다중 소스 검증 — 현재 다중 카메라는 단위 테스트까지만
확인했고 장비로 검증하지 않았다.

> 프레임 전달 방식은 [0006](#0006--워커-사이-프레임-전달을-최신-우선-버퍼로-한다)에서
> 정했다. 이 항목이 전제한 "워커별 분리 배포"는 그 결정으로 당분간 유보됐다.

## 0006 · 워커 사이 프레임 전달을 최신 우선 버퍼로 한다

**상태**: 확정

**배경**: [0005](#0005--worker를-역할별-워커로-분리)가 워커를 나눴지만 단계 사이를
무엇으로 잇는지는 열어 두었다. `stream`과 `inference`가 모두 동작하게 되면서
이 결정을 더 미룰 수 없었다.

핵심은 **수신 속도와 추론 속도가 다르다**는 것이다. 카메라는 20 FPS로 프레임을
내놓고 CPU에서 도는 탐지 모델은 그보다 느리다. 이 차이를 어떻게 다루느냐가
파이프라인의 성격을 정한다. 프레임을 쌓아두면 지연이 계속 커져 화면에 보이는 상태가
실제보다 과거가 되고, 생산자가 소비자를 기다리면 카메라 쪽 버퍼에 지연이 쌓인다.
**우리가 원하는 것은 "모든 프레임"이 아니라 "지금 누가 어느 자리에 있는가"다.**

**결정**: 두 가지를 정한다.

1. **전달 수단은 `worker/shared`의 최신 우선 프레임 버퍼다.**
   - 버퍼가 가득 차면 **가장 오래된 프레임을 버린다.** 생산자는 절대 블로킹하지 않는다.
   - 소비자는 버퍼에 남은 것 중 **가장 최근 프레임만** 가져가고 나머지는 버린다.
   - 기본 크기는 1이다. 실시간 파이프라인에서 필요한 것은 최신 한 장이다.
   - 버린 프레임 수를 세어 드러낸다. 이 값이 계속 늘면 추론이 수신을 못 따라간다는
     신호이며, 버퍼를 키울 게 아니라 샘플링 주기를 늘리거나 추론을 GPU로 옮긴다.
   - 표준 `queue.Queue`를 쓰지 않는다. 오래된 항목을 버리는 동작이 없어서, 꺼내고
     다시 넣는 방식으로 흉내 내면 생산자가 여럿일 때 어느 프레임이 남는지 보장할 수 없다.
2. **당분간 두 워커를 한 프로세스에서 스레드로 돌린다.** 조립은
   `worker/pipeline` 한 곳에서만 하고, `stream`과 `inference`는 서로를 import하지
   않는다. 둘 다 `shared`의 버퍼만 안다.

샘플링 판단은 수신 파이프라인에서 **한 번만** 내리고 그 결과를 학습용 이미지
저장기와 추론 버퍼에 함께 넘긴다. 각자 세면 디스크에 남은 이미지와 추론에 들어간
프레임이 어긋나, 나중에 탐지 결과를 이미지로 되짚을 수 없다.

**대안**:

- *별도 프로세스 + Redis 큐* — 0005가 노린 자원 분리를 유지하고 추론만 GPU 노드에
  둘 수 있다. 그러나 Redis 도입 자체가 아직 `후보` 단계이고, 프레임을 JPEG 등으로
  직렬화해 보내야 해서 인코딩 비용과 지연을 먼저 측정해야 한다. 파이프라인이 한 번도
  이어져 본 적 없는 상태에서 그 측정부터 시작하면 무엇이 병목인지 모른 채 구조를 고른다.
- *별도 프로세스 + 공유 메모리* — 외부 의존이 없고 프레임 복사가 가장 적다. 다만
  같은 머신에서만 되므로 GPU 노드 분리라는 목적을 달성하지 못하면서, 세그먼트 수명과
  경합 처리를 직접 만들어야 한다. 얻는 것에 비해 드는 비용이 크다.
- *버퍼 없이 동기 호출* — 가장 단순하지만 수신 루프가 추론 시간만큼 멈춘다.
  카메라가 늘면 모든 카메라의 수신이 추론 속도에 묶인다.
- *무제한 큐* — 프레임을 하나도 버리지 않는다. 추론이 조금만 느려도 메모리가 계속
  늘고 결과가 가리키는 시점이 과거로 밀린다. 실시간 모니터링에서는 손해다.

**결과**: 파이프라인이 실제로 이어져 탐지 결과를 눈으로 확인할 수 있고, 추론이
느려도 수신이 밀리지 않는다. 버린 프레임 수가 그대로 드러나 어디가 병목인지
숫자로 말할 수 있다.

대신 **0005가 노린 GPU/CPU 자원 분리를 당분간 못 한다.** 얼굴 탐지와 얼굴 인식이
붙으면 추론이 지금보다 무거워지므로, 수신과 같은 프로세스에 있는 것이 문제가 된다.
그때 버퍼를 프로세스 간 구현으로 바꾸는데, `stream`과 `inference`가 서로를 모르고
`shared`의 버퍼만 알기 때문에 고칠 곳이 버퍼 구현과 `pipeline` 조립 두 곳으로 좁혀진다.

또한 **프레임을 버리는 것이 기본 동작이다.** 모든 프레임을 봐야 하는 요구가
생기면(예: 사람이 화면을 가로지르는 구간의 전수 추적) 이 버퍼로는 안 되고 별도 경로가
필요하다. 얼굴이 보이는 순간이 드물다면 샘플링 주기 자체를 다시 봐야 한다.

**남은 일**: 실제 카메라와 실제 가중치로 초당 처리량과 드롭률 측정 — 측정 전에는
성능 수치를 문서에 적지 않는다. 측정 결과에 따라 프로세스 분리 시점 판단.
탐지 결과를 fastapi로 넘기는 방식은 여전히 `결정 필요`이며, 현재는 로그로만 출력한다.

## 0007 · recorder worker의 저장 구조와 보존 정책

**상태**: 대체됨([0011](#0011--영상-원본을-저장하지-않고-스냅샷만-남긴다))

**배경**: [0004](#0004--영상과-얼굴-이미지-저장소로-minio-채택)가 저장소를 MinIO로 정하면서
"무엇을 얼마나 저장할지"는 합의 사항으로 남겼다. 그 항목들은 지금도 `결정 필요`다.

**그런데 recorder worker를 먼저 만들었다.** 이 항목은 그 사실과 그때 내린 판단을
기록한다. 합의가 코드보다 늦은 상태이므로, 무엇이 임시이고 무엇이 확정인지
구분해 두지 않으면 기본값이 사실처럼 굳는다.

**결정**: 저장 구조는 아래대로 확정하고, 정책 값은 설정으로 두되 미합의임을
코드와 문서가 계속 드러내게 한다.

1. **recorder는 MediaMTX에서 직접 RTSP를 받아 FFmpeg으로 세그먼트를 만든다.**
   `stream` worker의 프레임을 받지 않는다. 저장 때문에 추론 경로가 느려지지 않게
   하려는 것이며, `-c copy`로 재인코딩하지 않아 CPU를 쓰지 않고 원본 화질을 유지한다.
2. **객체 저장소는 `ObjectStorage` 포트 뒤에 둔다.** 프로세스 밖으로 나가는 I/O이고,
   0004가 "MinIO SDK는 어댑터에만 둔다"고 정한 경계다. 구현체는 둘이다 — 운영용
   `minio`와 개발용 `local`. 로컬 어댑터가 있어야 MinIO 서버 없이 적재 경로 전체를
   검증할 수 있다. **`APP_ENV=prod`에서는 `local`을 거부한다.**
3. **객체 키는 `<카메라>/<YYYY-MM-DD>/<UTC 타임스탬프>.mp4`다.** 카메라를 맨 앞에 둔
   것은 카메라 단위 권한 분리와 일괄 삭제가 기간 단위보다 잦기 때문이고, 시각을
   UTC로 둔 것은 서버 시각대가 바뀔 때 같은 순간의 객체가 두 날짜에 걸치는 것을
   막기 위해서다.
4. **쓰는 중인 세그먼트를 올리지 않는다.** mp4는 moov atom을 마지막에 붙여서,
   FFmpeg이 아직 쓰는 파일을 올리면 재생 불가 객체가 저장소에 남는다. 가장 최근
   파일은 제외하되 일정 시간 변하지 않으면 FFmpeg이 죽은 것으로 보고 올린다.
5. **적재 실패 시 로컬 파일을 남긴다.** 지우면 재시도할 수 없어 그 시간대 영상이
   사라진다. 같은 키로 덮어쓰므로 중복 적재가 객체를 늘리지 않는다.
6. **보존 기간은 `RECORDING_RETENTION_DAYS`로 두고 기본값 30일을 준다.**
   자동 삭제를 함께 구현한다. **30일은 팀 합의값이 아니다.** 워커는 시작할 때 현재
   보존 기간과 저장소를 경고 로그로 남긴다.

**대안**:

- *합의 전까지 만들지 않기* — 0004가 정한 원래 방침이고, 지우기 어려운 데이터가
  쌓이는 것을 가장 확실히 막는다. 채택하지 않은 이유는 구현 지시가 있었기 때문이며,
  그 판단의 대가는 아래 결과에 적었다.
- *보존 기간에 기본값을 주지 않고 필수 설정으로 강제* — 값이 없으면 시작하지 않으므로
  합의 없이 운영에 뜨는 것을 코드가 막는다. [환경변수 규칙](../conventions/environment-convention.md)의
  "조용히 잘못 동작하면 안 되는 것에는 기본값을 두지 않는다"에도 맞는다.
  로컬 실행 편의를 위해 기본값을 두기로 했고, 대신 시작 경고로 대체했다.
- *스냅샷만 저장* — 저장량과 개인정보 노출이 가장 적다. 그러나 "무슨 일이 있었는지"를
  되짚는 용도에는 정지 이미지로 부족하고, 상시 녹화 여부 자체가 미합의라 지금
  좁히면 합의 결과를 앞질러 정하게 된다.
- *stream worker의 프레임을 재활용해 저장* — FFmpeg 프로세스가 하나 줄지만, 저장이
  추론과 같은 프레임 경로를 공유해 서로 속도에 영향을 준다. 재인코딩 비용도 생긴다.

**결과**: 영상이 객체 저장소에 쌓이고 보존 기간이 지나면 지워진다. 저장소 교체가
어댑터 교체로 끝나고, MinIO 없이도 적재 경로를 검증할 수 있다.

대신 **합의보다 코드가 앞선 상태가 남는다.** 기본값 30일이 검토 없이 운영까지
따라갈 수 있고, 접근 권한과 개인정보 고지는 여전히 비어 있다. 강의실 영상에는 학생의
얼굴이 담기고 미성년자가 포함될 수 있으므로 이건 기술 부채가 아니라 미해결 합의
사항이다. `prod`에서 로컬 저장소를 막고 시작 경고를 남기는 것으로 위험을 줄였을 뿐
없애지 못했다.

**남은 일**: 0004의 저장 정책 합의 — 특히 보존 기간과 접근 권한. 합의되면
`RECORDING_RETENTION_DAYS` 기본값과 recorder README의 표, `.env.example` 주석을
함께 갱신한다. 적재한 객체의 참조를 `fastapi`에 넘기는 경로는 전달 방식과 함께
아직 `결정 필요`다. 기본 버킷 이름이 이전 주제에서 온 `office-recordings`이므로
강의실 주제에 맞는 이름으로 바꿀지 함께 정한다. 실제 카메라를 붙인 녹화와
장시간·다중 카메라 안정성 측정도 남아 있다.

> FFmpeg·MediaMTX·MinIO를 붙인 전 구간 검증은 마쳤다. 그 과정에서 드러난 세 가지
> — FFmpeg `-strftime`이 로컬 시각을 쓴다는 것, Windows `terminate`가 마지막
> 세그먼트를 완성하지 못한다는 것, 완성되지 않은 파일이 적재될 수 있다는 것 —
> 은 코드에서 고쳤고 recorder README에 배경을 적었다.

## 0008 · 학생 상태 판정을 Rule Engine으로 분리하고 fastapi가 소유한다

**상태**: 확정

**배경**: 이 프로젝트가 관리자에게 최종적으로 보여 주는 것은 얼굴 인식 결과가 아니라
**"이 학생이 지금 재석인가, 자리를 잘못 앉았는가, 결석인가"** 다. 그 판정은 세 가지를
결합해야 나온다 — 모델이 준 학생 식별과 위치, 좌석 배치와 지정 좌석, 그리고 수업
시간표와 유예 시간.

여기서 갈리는 질문이 있었다. **모델이 최종 상태를 직접 내놓게 할 것인가.**
그렇게 하면 파이프라인은 짧아지지만, 유예 시간을 5분에서 10분으로 바꾸는 일에도
모델을 다시 학습하거나 추론 코드를 고쳐야 한다. 반대로 판정을 분리하면 어디에 둘지가
다시 문제가 된다 — 파이프라인 안의 워커인가, fastapi인가.

**결정**: 두 가지를 함께 정한다.

1. **모델은 상태를 결정하지 않는다.** 모델의 출력은 `student_id`, 위치(bbox),
   신뢰도까지다. `PRESENT`, `ABSENT`, `WRONG_SEAT` 같은 업무 어휘를 추론 코드와
   탐지 결과 스키마에 넣지 않는다. 상태는 그 출력에 좌석 배치·수업 시간표·유예
   시간을 결합하는 **규칙**이 만든다.
2. **그 규칙을 `webapps/fastapi`가 소유한다.** `worker`에 상태 판정 워커를 두지
   않는다. 판정에 필요한 입력(학생 원장, 지정 좌석, 좌석 ROI, 수업 세션)이 모두
   fastapi의 저장소에 있고, 판정 결과의 소비자(화면, 조회 API, 이력, 이후 RPA)도
   전부 fastapi 쪽이기 때문이다. 워커에 두면 같은 데이터를 양쪽이 들고 있어야 한다.

함께 정하는 것:

- **판정 기준값은 코드에 박지 않는다.** 유예 시간, 신뢰도 임계값, 좌석 판정 여유는
  설정으로 둔다. 값 자체는 실제 촬영과 운영 요구로 정하며 아직 `결정 필요`다.
- **판정은 명시적인 쓰기 요청에서만 수행한다.** 목록 조회 GET이 시간 정책을 실행해
  상태를 바꾸지 않는다. 조회가 부작용을 일으키면 화면을 두 번 연 것과 한 번 연 것의
  결과가 달라진다.
- **미관측을 부재로 바꾸지 않는다.** 카메라가 죽었거나 얼굴이 가려진 것과 학생이
  자리에 없는 것은 다른 사실이다. 유예 시간을 넘긴 미탐지만 `ABSENT`가 된다.

**대안**:

- *모델이 최종 상태까지 출력* — 파이프라인이 짧고 fastapi가 얇아진다. 그러나 출결
  정책이 바뀔 때마다 모델·추론 코드를 건드려야 하고, 왜 그 상태가 나왔는지 설명할
  수 없다. 출결은 사람에게 불이익을 줄 수 있는 판정이라 근거를 되짚을 수 있어야 한다.
- *`worker/state` 워커에 판정을 둔다* — 파이프라인 안에서 상태까지 만들어 fastapi에
  결과만 넘긴다. 지연이 가장 짧다. 그러나 판정에 필요한 학생·좌석·시간표 데이터를
  워커가 따로 읽어야 해서 저장소 접근 지점이 둘로 늘고, 정책이 바뀔 때 고칠 곳도
  둘이 된다. 이 대안을 위해 만들어 두었던 `worker/state` 디렉터리는 이 결정으로 지운다.
- *판정을 두되 fastapi와 워커에 나눠 둔다* — 즉시 판정(좌석 일치)은 워커가, 시간
  기반 판정(결석)은 fastapi가 맡는 안. 규칙이 두 곳으로 갈려 "이 상태는 누가 만들었나"를
  매번 따져야 한다.

**결과**: 출결 정책을 바꾸는 일이 fastapi의 설정과 규칙 함수 수정으로 끝난다. 모델
교체가 업무 규칙에 영향을 주지 않고, 규칙 변경이 모델 재배포를 부르지 않는다.
판정 근거(어떤 탐지 이벤트로 이 상태가 됐는지)를 한 서비스 안에서 이력으로 남길 수 있다.

대신 **탐지 결과가 fastapi까지 도달해야 상태가 만들어진다.** 전달 방식이 아직
`결정 필요`이므로 그 경로가 생기기 전까지 자동 상태 갱신은 동작하지 않는다.
판정 부하도 fastapi가 진다. 카메라와 학생이 늘어 판정이 요청 경로를 무겁게 하면
그때 분리를 다시 논의한다.

**남은 일**: 탐지 결과 전달 방식 확정. 유예 시간·신뢰도 임계값·좌석 판정 방식의
실제 값 확정(실제 촬영 결과가 필요하다). `IN_CLASSROOM`(자리에는 없지만 교실 안에
있음)은 지속적 위치 추적이 필요해 MVP 범위 밖이며, 도입 시 규칙과 필요한 카메라를
새 항목으로 정한다.

## 0009 · 추론 책임을 모델과 실행으로 나눈다

**상태**: 확정

**배경**: 목표 파이프라인은 사람 탐지 → 얼굴 탐지 → 얼굴 인식 → 갤러리 대조 순서로
모델을 세 번 이상 거친다. 이 모델들을 어디에 둘지 정해야 했는데, 저장소에는 이미
겹치는 두 곳이 있었다. `deeplearning`은 "모델 추론 서비스"를 표방하지만 코드가 없고,
`worker/inference`는 코드가 있고 실제로 YOLO를 직접 부른다.

둘 다 "추론"이라고 부르는 동안에는 새 모델을 어디에 추가할지 매번 갈린다.

**결정**: 이름이 아니라 **책임의 종류**로 나눈다.

| 디렉터리 | 책임 | 여기에 두지 않는 것 |
| --- | --- | --- |
| `deeplearning` | 모델 로딩·전처리·추론·후처리와 **탐지 결과 스키마 정의**. 모델을 아는 유일한 곳 | 스트림 연결, 프레임 수명 관리, 업무 해석 |
| `worker/inference` | 프레임 버퍼에서 프레임을 꺼내 `deeplearning`을 호출하고, 결과를 다음 단계로 내보내는 **실행 단계** | 모델 종류·가중치·전처리 세부 |

- **`deeplearning`이 모델 교체의 유일한 진입점이다.** 얼굴 탐지기를 SCRFD에서 다른
  것으로 바꾸거나 인식 모델을 AdaFace에서 ArcFace로 바꿔도 `worker/inference`는
  고치지 않는다.
- **`worker/inference`는 모델 이름을 모른다.** 무엇을 탐지했는지가 아니라 언제
  호출하고 실패하면 어떻게 할지를 다룬다.
- **둘 다 업무 의미를 붙이지 않는다.** 출력은 `student_id`와 bbox와 신뢰도까지이며,
  상태 해석은 [0008](#0008--학생-상태-판정을-rule-engine으로-분리하고-fastapi가-소유한다)에
  따라 fastapi가 한다.
- `deeplearning`을 별도 프로세스로 띄울지 라이브러리로 import할지는 이 항목이
  정하지 않는다. 경계가 지켜지면 나중에 어느 쪽으로도 갈 수 있다.

**현재 코드는 이 결정을 아직 만족하지 않는다.** `worker/inference`가 ultralytics를
직접 부르고 `deeplearning`에는 코드가 없다. 이는 `deeplearning` 구현 전의 잠정
상태이며, 구현 시 모델 호출을 그쪽으로 옮긴다.

**대안**:

- *`deeplearning`이 전부 담당하고 `worker/inference`를 폐기* — 추론 관련 코드가 한
  곳에 모인다. 그러나 프레임 버퍼 소비, 연속 실패 처리, 종료 신호 같은 **파이프라인
  수명 관리**가 모델 코드와 섞인다. 그 부분은 모델과 무관하게 유지되어야 하는 코드다.
- *`worker/inference`가 전부 담당하고 `deeplearning`을 폐기* — 지금 코드에 가장
  가깝다. 그러나 모델이 세 개 이상으로 늘고 GPU 노드로 분리될 가능성이 있는 상태에서
  모델을 워커 안에 묻으면, 나중에 떼어낼 때 파이프라인 코드까지 딸려간다.
- *경계를 정하지 않고 필요할 때 판단* — 매 작업마다 같은 논의를 반복하게 되고, AI
  에이전트는 지시가 없으면 자기가 보고 있는 디렉터리에 모델 코드를 만든다.

**결과**: 새 모델을 붙일 때 "`deeplearning`에 넣는다"는 답이 고정된다. 모델 없이도
`worker/inference`의 수명 관리와 실패 처리를 테스트할 수 있고, 실제로 지금 그렇게
테스트하고 있다. 대신 `deeplearning` 구현 전까지 경계를 어기는 코드가 남아 있고,
호출 방식(라이브러리 / 별도 프로세스)이 정해질 때까지 그 사이의 계약이 임시다.

**남은 일**: `deeplearning` 구현과 `worker/inference`의 모델 호출 이관. 사용할
얼굴 탐지·인식 모델 확정(SCRFD·AdaFace·ArcFace가 `후보`이며 비교가 필요하다).
`deeplearning` 호출 방식 확정. 현재 `worker/inference`가 탐지하는 `cell phone`
클래스는 이전 주제(통화 판정)에서 온 것으로 새 주제에서 쓰이지 않으며, 모델 이관
때 함께 정리한다.

## 0010 · MVP 제품 사용자를 관리자 하나로 한정한다

**상태**: 확정

**배경**: 이 시스템이 대체하려는 일은 **관리자가 강의실을 돌며 학생을 일일이
확인하는 것**이다. 학생은 시스템의 관찰 대상이지 사용자가 아니다. 그런데 제품
경계를 넓게 잡으면 학생 로그인, 본인 상태 조회, 학생 대상 알림이 따라 들어오고,
그때부터 인증·권한·개인 데이터 노출 범위를 함께 설계해야 한다.

동시에 반대 방향의 문제가 있다. 현재 `webapps/fastapi`에는 **인증이 전혀 없다.**
누구나 강의실 좌석 현황을 볼 수 있는 상태다. 여기에 학생 얼굴과 출결이 붙으면
그대로 둘 수 없다.

**결정**: 두 가지를 함께 정한다.

1. **MVP의 제품 사용자는 관리자 한 종류다.** 학생·보호자 로그인, 학생 대상 알림,
   본인 출결 조회는 MVP 범위 밖이다. 화면과 API를 역할별로 나누지 않고, 권한 분기를
   미리 만들지 않는다.
2. **앱 자체 로그인을 지금 만들지 않되, 인증 없는 상태를 운영에 올리지 않는다.**
   운영 접근을 무엇으로 막을지(내부망 한정 / 신뢰된 reverse proxy / 상위 시스템
   인증 위임)는 `결정 필요`이며, **정해지기 전까지 `APP_ENV=prod` 배포를 하지 않는다.**
   이 제약은 local·dev 개발을 막지 않는다.

**대안**:

- *지금 역할 기반 인증을 다시 넣는다* — 배포를 막지 않는다는 점이 가장 크다. 그러나
  MVP에서 실제로 필요한 역할이 하나뿐이라 로그인·토큰·권한 판정 코드가 전부 사용자
  한 종류를 위한 것이 된다. 그 코드는 이전 버전에서 이미 만들었다가 제품 범위 축소로
  지운 것이며, 근거 없이 되돌리는 셈이 된다.
- *학생 사용자를 처음부터 포함* — 최종 형태에 가깝다. 그러나 본인 출결·얼굴 데이터
  노출 범위가 개인정보 합의와 묶여 있어([0004](#0004--영상과-얼굴-이미지-저장소로-minio-채택)),
  합의 전에 만들면 지우기 어려운 화면과 API가 먼저 생긴다.
- *접근 통제 없이 운영에 올린다* — 선택지로 두지 않는다. 학생 얼굴과 출결이 걸린
  화면을 인증 없이 노출하는 것이기 때문이다.

**결과**: 화면과 API가 단순해지고, 권한 분기 없이 기능 자체에 집중할 수 있다.
접근 통제 결정이 배포를 막는 항목으로 명시돼 "일단 띄우고 나중에 막자"가 되지 않는다.
대신 **운영 배포가 이 결정 하나에 묶인다.** 학생 사용자를 나중에 추가할 때 인증과
권한 모델을 그 시점에 처음부터 설계해야 하고, 그때 이 항목을 대체하는 새 항목이 필요하다.

**남은 일**: 운영 접근 통제 방식 확정. 관리자가 여러 명이 되고 누가 무엇을 봤는지
남겨야 하면 감사 기록과 계정 체계를 새 항목으로 정한다. 학생·보호자 알림은 관리자
확인을 거친 뒤 RPA가 수행하는 흐름이 전제이며, 대상과 채널은 아직 `결정 필요`다.

## 0011 · 얼굴 등록 실시간 경계와 데이터 수명

**상태**: 확정

**배경**: 얼굴 등록은 브라우저 프레임마다 분석 결과와 다음 안내를 돌려줘야 한다.
브라우저가 모델 서비스에 직접 연결하면 외부 진입점이 둘이 되고, 등록 세션과 원본의
삭제 책임도 갈라진다. 또한 미완료 얼굴 데이터와 완료된 등록 원본은 수명이 다르다.

**결정**:

1. 브라우저는 FastAPI의 등록 세션별 WebSocket으로 프레임을 보낸다. FastAPI가 등록
   상태, pose quota, 완료율과 안내를 소유한다.
2. FastAPI는 추론 포트를 통해 중앙 `deeplearning` 서비스를 호출한다. 서비스 간 실제
   프로토콜은 HTTP로 두며 타임아웃을 반드시 적용한다. local 테스트는 동일 포트의 합성
   분석기를 사용한다.
3. 한 번에 활성 등록 세션은 하나만 허용한다.
4. 후보·거부 프레임은 영구 저장하지 않는다. 승인된 프레임만 얼굴 전용 MinIO 영역에
   저장하며, WebSocket 단절 또는 취소 시 미완료 세션의 원본과 메타데이터를 삭제한다.
5. 완료된 유효 원본은 재학 기간 또는 동의 철회까지 보관한다. API와 로그에는 원본,
   객체 키와 embedding을 노출하지 않는다.
6. 동의의 정본은 외부 문서다. 시스템에는 이를 확인한 관리자 식별자와 시각만 기록한다.

**결과**: 브라우저의 호출 대상과 업무 판단 주체가 FastAPI 하나로 유지된다. 연결 종료가
곧 미완료 데이터 폐기를 뜻하므로 이어하기는 지원하지 않는다. WebSocket 재연결만으로
세션을 복구할 수 없으며 새 등록을 시작해야 한다.

**남은 일**: 운영 관리자 인증과 얼굴 데이터 접근 통제, 재학 종료 자동 삭제 작업,
실제 SCRFD·MediaPipe·AdaFace 모델 비교 및 중앙 추론 HTTP 어댑터의 운영 배포 검증.

## 0014 · GitHub Actions로 develop 병합 시 CI 검증과 GHCR 이미지 자동 빌드

**상태**: 확정

**배경**: `webapps/fastapi`와 `worker`의 컨테이너 이미지는 그동안 팀원이 로컬에서
수동으로 빌드해 GHCR에 push해 왔다(가장 최근은 2026-08-12). `develop`에 병합이
계속 들어오는 상황에서 수동 push는 누락되기 쉽고, 실제로 배포된 이미지가 `develop`
상태와 어긋날 위험이 있다. 동시에 문서만 바뀐 PR까지 매번 빌드·테스트를 기다리게
하면 병합이 느려진다.

**결정**:

1. `.github/workflows/ci.yml` 하나로 PR 검증과 병합 후 이미지 빌드를 함께 처리한다.
   `pull_request`(대상 `develop`)와 `push`(`develop`) 두 이벤트로 트리거한다.
2. `dorny/paths-filter`로 변경 경로를 판정해 `webapps/fastapi/**` 변경 시에만 fastapi
   검증 job을, `worker/**` 변경 시에만 worker 검증 job을 돌린다. 두 경로에 속하지 않는
   변경(문서 등)은 모든 job이 스킵되며, 깃허브는 스킵된 job을 성공으로 취급하므로
   필수 상태 체크로 지정해도 병합을 막지 않는다. `paths-ignore`로 워크플로우 자체를
   안 돌게 하는 방식은 쓰지 않는다 — 트리거되지 않은 필수 체크는 영원히 "대기 중"으로
   남아 오히려 병합을 막기 때문이다. 워크플로우 파일 자신(`.github/workflows/ci.yml`)은
   양쪽 필터에 모두 넣는다. 넣지 않으면 CI를 고치는 PR이 아무 검증 없이 병합된다.
3. fastapi 검증은 `ruff check` → `ruff format --check` → `mypy` → `pytest -q` 순으로
   돌린다(CLAUDE.md가 병합 전 필수로 정한 순서와 같다). worker 검증은 `pytest -q`만
   돌린다 — worker에는 아직 lint·타입 검사 설정이 없다.
4. 브랜치 보호 규칙에 등록할 필수 체크는 `ci-gate` job 하나로 고정한다. 깃허브의 필수
   체크는 job id가 아니라 job의 `name` 표시값으로 등록되므로, 검사 job의 이름을 바꾸면
   필수 체크가 이름 불일치로 조용히 풀린다. 이름이 고정된 게이트를 두면 검사 job을
   자유롭게 늘리고 고칠 수 있다. 게이트는 `if: always()`로 돌면서 선행 job 중
   `failure`·`cancelled`가 있으면 실패하고, `skipped`는 통과로 본다.
5. 이미지 빌드·GHCR push는 `push` 이벤트(즉 `develop` 병합 이후)에서만, 그리고 해당
   서비스 검증이 통과한 뒤에만 실행한다. PR 단계에서는 절대 push하지 않는다.
   동시성 설정의 `cancel-in-progress`는 `pull_request`에만 적용한다 — `push`까지 취소하면
   연달아 병합될 때 앞 커밋의 이미지가 영영 올라가지 않는다(뒤 커밋이 다른 서비스만
   건드리면 앞 커밋의 빌드를 아무도 대신해 주지 않는다).
6. 인증은 `GITHUB_TOKEN`만 쓴다(별도 PAT을 만들지 않는다). 워크플로우 최상위 권한은
   `contents: read`로 내리고, push가 필요한 job에서만 `packages: write`를 올린다.
   이미지 이름은 `ghcr.io/${{ github.repository_owner }}` 뒤에
   `classroom-monitoring-fastapi`를 붙인 것으로 하며, 조직명을 하드코딩하지 않고
   저장소 소유자를 그대로 쓴다. 태그는 `develop`과 `sha-<짧은 커밋 해시>` 두 가지다.
   **`latest`는 붙이지 않는다** — `.docker/compose.main.yml`의 기본값이 `:latest`라
   `develop` 병합 결과가 곧바로 운영 서버로 흘러가기 때문이다. `latest`는 `main` 배포
   시점에만 붙인다.
7. **`worker` 이미지는 자동 빌드하지 않는다.** 이미지가 14.9GB라(torch 휠이 번들하는
   CUDA 런타임만 3.6GB) 깃허브 호스팅 러너의 디스크 여유를 넘길 위험이 크고, Actions
   캐시는 저장소당 10GB 상한이라 `mode=max`로 밀어 넣으면 들어가지도 못하면서 fastapi
   캐시까지 밀어낸다. 이미지 경량화 전까지는 GPU가 달린 PC에서 수동으로 빌드해 push한다.
   MVP 단계에서는 검증 자동화의 값어치가 크고 무거운 빌드의 값어치는 작다는 판단이다.
8. `worker/recorder`는 이번 빌드 대상에서 뺀다. 전용 Dockerfile이 없고, 결정
   0011(영상 원본 미저장)에 따라 공용 서버에 배포하지 않기 때문이다.

**대안**:

- **`paths-ignore`로 문서 변경 시 워크플로우 자체를 트리거하지 않기** — 검토했으나,
  브랜치 보호 규칙에서 같은 체크를 필수로 지정하면 트리거되지 않은 체크가 "대기 중"
  상태로 남아 병합을 막는 깃허브의 알려진 함정이 있어 채택하지 않았다.
- **레포지토리 전체를 이미지 하나로 빌드** — fastapi와 worker는 런타임 의존성과 배포
  대상 서버가 다르다(worker는 GPU 서버, fastapi는 별도). 서비스별로 독립된 이미지를
  유지하는 기존 구조(Dockerfile 두 개)를 그대로 따랐다.
- **GHCR 인증에 개인 액세스 토큰(PAT) 사용** — 같은 저장소 안에서 push하는 것뿐이라
  `GITHUB_TOKEN`의 `packages: write` 권한으로 충분하다. PAT은 별도 시크릿 관리 부담과
  유출 위험을 늘릴 뿐이라 채택하지 않았다.
- **MVP 단계에는 CI 자동화를 통째로 미루고 계속 수동 빌드** — 검토했으나 채택하지
  않았다. 최근 4주 `develop` 커밋이 130개, 기여자가 5명 안팎이라 작업 간 충돌 위험이
  가장 큰 시기가 지금이다. 미루면 그 비용을 사람이 감당해야 한다. 또한 지금 도입을
  주저하게 만드는 요인은 worker 이미지 빌드 하나뿐인데, 그것 때문에 비용이 사실상
  0인 검증 자동화까지 버리는 것은 균형이 맞지 않는다. 대신 무거운 조각(worker 빌드)만
  떼어내는 방식(결정 7)을 택했다.
- **검사 job(`fastapi-checks`·`worker-checks`)을 직접 필수 체크로 등록** — 검토했으나
  채택하지 않았다. 필수 체크는 job의 `name` 표시값으로 등록되므로 이름을 바꾸는 순간
  조용히 풀린다. 검사 job을 늘릴 때마다 브랜치 보호 설정을 함께 고쳐야 하는 부담도
  생긴다. 이름이 고정된 `ci-gate` 하나만 등록하는 방식(결정 4)이 더 견고하다.
- **worker 이미지도 함께 자동 빌드** — 검토했으나 채택하지 않았다. 근거는 결정 7에 있다.
  러너 디스크 확보 스텝을 넣고 캐시를 `mode=min`으로 낮추면 될 가능성은 있지만,
  실제로 통과하는지 확인하지 않은 설정을 넣으면 매 병합마다 빨간불이 켜져 CI 신뢰도만
  깎인다. 경량화가 끝난 뒤 실측하고 넣는다.

**결과**: `develop`에 실제로 반영된 fastapi 변경만 이미지로 남는다. 문서 전용 PR은
빌드·테스트 대기 없이 병합할 수 있다. 검증은 자동화되지만 worker 이미지 배포는 여전히
사람이 기억해야 하는 수동 작업으로 남는다 — 이 결정이 감수하는 부분이다.

`latest` 태그를 더 이상 갱신하지 않으므로 `.docker/compose.main.yml`의 기본값
`:latest`는 **2026-08-12에 수동으로 push한 이미지에 고정된 채로 남는다.** 자동 빌드
결과를 서버에 반영하려면 `FASTAPI_IMAGE` 환경변수로 `:develop`이나 `:sha-<해시>`를
지정해야 한다. compose 기본값 자체를 바꾸는 것은 배포 정책이라 팀 합의가 먼저다.

GHCR 패키지 쓰기 권한(저장소 Settings → Actions → Workflow permissions)과 브랜치 보호
규칙의 필수 상태 체크 지정은 저장소 설정 영역이라 이 결정만으로 자동 적용되지 않는다 —
사람이 한 번 켜야 한다.

**남은 일**:

- 저장소 Settings에서 Actions 쓰기 권한 켜기.
- 워크플로우를 1~2주 돌려 오탐이 없는지 확인한 뒤, `develop` 브랜치 보호 규칙에
  **`ci-gate`** 를 필수 체크로 등록한다. 처음부터 필수로 걸지 않는 이유는 MVP 속도를
  CI 오탐에 묶지 않기 위해서다. 같은 화면에서 "Require branches to be up to date before
  merging"도 함께 켠다 — PR 체크는 통과했지만 그 뒤 `develop`이 바뀌어 생기는
  의미적 충돌은 이 설정으로만 막힌다.
- 첫 push로 생성되는 GHCR 패키지는 기본 private이고 저장소와 자동 연결되지 않는다.
  배포 서버에서 pull하려면 패키지 visibility 또는 pull 자격 증명을 한 번 설정해야 한다.
- `worker`에 lint·타입 검사 설정이 없어 검증이 `pytest`뿐이다. `webapps/fastapi`의 ruff
  설정을 옮겨 `worker/pyproject.toml`을 만들고 검사를 추가하는 것을 검토한다.
- CI는 Python 3.12로 도는데 팀의 로컬 환경에는 3.14가 섞여 있다. 지원 버전 확정은
  `webapps/fastapi/pyproject.toml` 주석이 남긴 **결정 필요** 항목이며, 확정되면 CI의
  `python-version`과 함께 갱신한다.
- `worker` 이미지 경량화가 끝나면 자동 빌드 job 도입을 새 항목으로 기록한다.
  `worker/recorder`를 배포 대상에 넣기로 결정되면 전용 Dockerfile과 빌드 job을 추가한다.
- `main` 브랜치 배포 시점의 릴리스 태깅 전략(`latest`를 언제 붙일지)은 아직 다루지 않았다.

## 0015 · 서비스 설정을 local/dev/prod .env와 공용 config/settings.yml로 분리한다

**상태**: 확정

**배경**: `webapps/fastapi`와 `worker`의 네 서브패키지(`stream`·`inference`·`recorder`·
`pipeline`) 모두 `.env` 파일 하나에 "환경마다 달라야 하는 값(비밀값·서비스 주소·
로컬 대역과 실제 외부 연동을 고르는 백엔드 선택)"과 "환경과 무관하게 항상 같은 값
(재시도 횟수·타임아웃·신뢰도 임계값)"이 섞여 있었다. local(개발자 PC)·dev(공용 GPU
서버)·prod(배포) 세 실행 환경을 명확히 나누려는 작업 중 이 뒤섞임이 값을 옮길 때마다
걸림돌이 됐다. 조사 과정에서 `webapps/fastapi`의 `Settings`(`app/shared/config.py`)에
없는 필드(JWT·인증·알림·직원 관련 18개)가 실제 `.env`에는 남아 있는 것도 확인했다 —
`extra="ignore"`라 조용히 무시되던 이전 "사무실 모니터링" 주제의 죽은 값이다.

**결정**:

1. 서비스별 설정 파일을 둘로 나눈다. `<서비스>/.env.{local,dev,prod}`에는 환경 의존
   설정과 비밀값을(예: `APP_ENV`, `DATABASE_MODE`, `DATABASE_URL`, `INFERENCE_DEVICE`,
   `OBJECT_STORAGE_BACKEND`와 접속 정보), `<서비스>/config/settings.yml`에는 일반 설정과
   판정 기준값을 둔다(예: 타임아웃, 재시도 횟수, quota, 신뢰도 임계값). 분류 기준은
   [환경변수 규칙](../conventions/environment-convention.md)의 4단 표를 그대로 쓴다.
2. 실제 OS 환경변수 `APP_ENV`(셸에서 export하거나 docker-compose `environment:`로 주입)가
   어떤 `.env.{app_env}` 파일을 읽을지 정한다. export하지 않으면 `local`로 본다.
   `config/settings.yml`은 환경과 무관하게 서비스마다 하나다.
3. 값을 읽는 우선순위는 실제 OS 환경변수 > `.env.{app_env}` 파일 >
   `config/settings.yml` 순으로 고정한다(Pydantic Settings의
   `settings_customise_sources`). worker 네 서브패키지는
   `worker/shared/settings_sources.py`의 공용 함수 하나로 이 순서를 통일해서 쓴다.
4. `.env.example`은 `Settings` 클래스의 실제 필드만 담도록 다시 쓴다. 코드에 없는
   필드는 옮기지 않고 버린다 — 이번에 확인한 18개 죽은 변수가 대상이다.
5. 필드의 필수 여부와 Python 기본값은 바꾸지 않는다. 이 결정은 "어느 파일에 있어야
   찾기 쉬운가"만 다루며, 검증 강도를 높이거나 낮추지 않는다.

**대안**:

- **모든 값을 `.env.{local,dev,prod}`에만 두고 yml을 두지 않는다** — 지금까지 해오던
  방식이다. 그러나 재시도 횟수나 신뢰도 임계값처럼 코드 리뷰로 값을 조정하고 싶은
  항목까지 커밋되지 않는 개인 파일에 있어 "지금 운영 중인 값이 무엇인지" 저장소만
  보고는 알 수 없었다. 이번 조사에서 드러난 죽은 변수 문제도 이 방식에서 계속
  반복될 수 있다.
- **프로젝트 전체를 env 파일 하나로 통합** — worker 네 서브패키지는 독립 실행(카메라
  수신만, 추론만 등)을 지원하기 위해 서로 다른 필수 값을 요구하도록 의도적으로 설계돼
  있다([결정 0005](#0005--worker를-역할별-워커로-분리)). 하나로 합치면 이 독립 실행이
  깨진다.
- **`.env` 파일 이름을 그대로 두고 내용만 환경별 주석으로 구분** — 파일 하나에 세
  환경 값이 다 있으면 실수로 다른 환경 값을 활성화하기 쉽고, "지금 이 프로세스가 어떤
  값을 읽고 있는지"가 파일을 열어보기 전까지 드러나지 않는다.

**결과**: 서비스가 읽는 값이 "커밋된 공용 기본값(yml)"과 "환경별 비공개 값(.env.*)"으로
분리돼, 코드 리뷰로 조정할 수 있는 값과 그렇지 않은 값이 파일 위치만으로 구분된다.
worker 조립 실행(`pipeline`)의 "같은 변수가 여러 파일에 흩어지지 않게 한다"는 기존
설계도 그대로 유지된다. 대신 실행 전에 `APP_ENV`를 export해야 하는 절차가 하나
늘었다 — export하지 않으면 항상 `local`로 동작하므로 로컬 개발은 지금과 다르지 않다.

이 결정은 각 서비스가 설정을 **어떻게 읽는가**만 다룬다. `docker-compose` 통합 실행
수단의 공식화와 배포 환경·방식 자체는 여전히 `결정 필요`로 남는다
([미결정 항목](./README.md#미결정-항목) 참고) — `.docker/`와 `env/*.env`(docker compose
전용 값 파일)는 이번 결정의 대상이 아니다.

**남은 일**: 팀원 각자 실제 `.env`(구 이름) 값을 새 `.env.local`/`.env.dev`/`.env.prod`로
옮겨야 한다 — 자동 이관하지 않았다. `worker/recorder`의 `OBJECT_STORAGE_BUCKET` 기본값
`office-recordings`처럼 이전 주제의 이름이 남은 값은 이번에 위치만 옮기고 이름은
바꾸지 않았다([결정 0007](#0007--recorder-worker의-저장-구조와-보존-정책)이 이미
"결정 필요"로 남긴 별도 사안). `docs/architecture/decisions.md` 자체의 기존 결함(이
문서의 0011~0013 번호 대역에 목차만 있고 본문이 빠진 항목 세 개)은 이번 작업과
무관하게 발견했으며 별도로 다뤄야 한다.

## 0016 · 자연어 검색에서 LLM은 계획만 만들고 검증·조회는 fastapi가 소유한다

**상태**: 확정

**배경**: 운영자가 "오늘 6시부터 7시 사이에 교실에 누가 들어왔어?" 같은 질문으로
탐지 기록을 찾고 싶다. 질문을 해석할 수 있는 것은 LLM이지만, LLM에게 데이터 접근을
맡기면 **응답 품질이 그대로 데이터 접근 통제가 된다.** 모델이 규격을 벗어난 순간
잘못된 조회이거나 조회해서는 안 되는 범위가 된다.

번호가 0016인 이유는 이 파일의 목록 표와 본문 헤딩이 어긋나 있어(0011 중복, 표의
0012·0013에 해당하는 본문 없음, 본문은 0011 다음이 0014) 비어 보이는 번호를 주워
쓰면 충돌하기 때문이다. 0015는 미병합 브랜치가 이미 쓰고 있다.

**결정**:

1. LLM의 책임은 **자연어를 검색 계획 JSON으로 바꾸는 데서 끝난다.** DB에 접근하지
   않고, 도구를 갖지 않으며, 질의 문자열을 만들지 않는다.
2. fastapi가 계획을 검증한다. 알 수 없는 키, 허용 목록 밖의 `intent`, 시각대 없는
   시각, 상한을 넘는 값, 객체가 아닌 최상위 JSON을 모두 거부한다. 검증을 통과한
   도메인 값만 기존 저장소 포트에 들어간다. **모델 출력이 질의 조각으로 흘러가는
   경로를 두지 않는다.**
3. 검증은 순수 모듈(`app/llm_search/planning.py`)에 두고 어댑터에 나누지 않는다.
   LLM 없이 시험할 수 있어야 하고, 방어선이 두 곳이면 어느 쪽이 진짜인지 알 수 없다.
4. 통신은 llama.cpp 서버의 OpenAI 호환 HTTP API로 하고 타임아웃을 반드시 적용한다.
   결정 0001의 네 경계 중 "추론 클라이언트"이며 새 경계가 아니다. LLM 없이 도는
   대역(`stub`)을 기본 모드로 두어 개발·테스트가 GPU 서버에 매이지 않게 한다.
5. 조정과 거절을 구분한다. 기간이나 결과 수가 상한을 넘으면 거절하지 않고 줄인 뒤
   **줄였다는 사실을 응답과 화면에 남긴다.** 조용히 줄이면 사용자가 부분 결과를
   전부로 읽는다.
6. 검증을 통과한 계획을 응답에 그대로 노출한다. 왜 이 결과가 나왔는지 확인할 수
   없으면 자연어 검색을 신뢰할 수 없다. 모델 원문은 로그에만 남기고 응답에 넣지
   않는다 — 프롬프트에 실은 카메라·강의실 식별자가 되돌아 나올 수 있다.

**대안**:

- **LLM이 MongoDB 질의를 직접 만든다**: 표현력은 가장 높지만 모델 출력이 그대로
  질의가 되어 검증할 지점이 없다. 결정 0008이 "판정은 fastapi가 소유한다"고 정한
  것과 정반대 방향이다.
- **LLM에게 조회 도구를 주고 결과까지 요약하게 한다**(function calling): 자연스럽지만
  모델이 몇 번, 어떤 범위로 조회할지 우리가 통제하지 못한다. llama-server가 추론
  워커와 GPU를 나눠 쓰는 상황에서 호출 횟수를 모델이 정하게 둘 수 없다.
- **기존 규칙 기반 검색을 확장한다**(`video_monitoring`의 한국어 토큰 매칭): 외부
  의존이 없고 결정적이지만, 표현을 늘릴 때마다 코드를 고쳐야 하고 조사·어순 변화를
  따라가지 못한다. 이 결정은 그 화면을 대체하지 않고 나란히 둔다.
- **LLM 없이 폼 검색만 제공한다**: 가장 단순하지만 요청받은 기능이 아니다.

**결과**: 모델이 실패하는 방식이 "잘못된 조회"가 아니라 "조건을 만들지 못했다"로
바뀐다. 모델을 바꿔도 검증 계약은 그대로다. 반대로 표현력은 계약에 갇힌다 — 계약에
없는 조건은 질문에 담아도 무시되고, 새 조건을 지원하려면 계약과 프롬프트와 검증을
함께 고쳐야 한다.

llama-server는 추론 워커와 같은 GPU를 쓴다. 인증이 없는 상태(결정 0010)라 검색이
몰리면 탐지 파이프라인이 느려질 수 있다. 질문 길이 상한과 생성 토큰 상한이 지금 있는
유일한 제동 장치이며, **이 위험을 감수하고 진행한다.**

**남은 일**:

- 탐지 이벤트 수집 경로가 아직 연결되지 않았다. `/internal/inference/events`를
  호출하는 코드가 저장소에 없어 이 기능의 결과가 실제로 비어 있다.
- 학생 식별이 붙으면 계획 계약에 학생 조건을 추가한다. 지금 넣으면 채울 데이터가
  없어 항상 0건인 필터가 된다.
- Gemma가 이 프롬프트로 규격에 맞는 JSON을 얼마나 안정적으로 내는지 실측이 필요하다.
  `response_format`을 `json_object`에서 `json_schema`로 조일지도 그 결과로 정한다.
- 고도화 단계에서 n8n이 Tool로 부를 엔드포인트는 `/api/v1`이 아니라 `/internal`에
  속한다(api-convention). 지금은 브라우저가 쓰는 제품 API 하나만 둔다.
- 동시 실행 제한은 두지 않았다. GPU 경합이 실제로 관측되면 얼굴 등록의 "활성 세션
  하나" 방식을 참고해 추가한다.
