# GPT 코딩 프롬프트

저장소를 직접 읽지 못하는 도구(웹 GPT 등)로 코드를 작성할 때 사용한다.

Claude Code나 Codex는 저장소 안의 규칙 문서를 스스로 읽지만, 웹 GPT는 읽지 못한다.
**규칙을 대화에 직접 넣어 주지 않으면 지켜지지 않는다.** 이 문서는 그 붙여넣을 내용을
모아 둔 것이다.

## 쓰는 순서

1. 새 대화를 열고 **[1단계](#1단계-역할-지정)** 를 붙여넣는다.
2. 이어서 **[2단계](#2단계-프로젝트-규칙-붙여넣기)** 를 붙여넣는다. 대화당 한 번이면 된다.
3. 작업할 때마다 **[3단계](#3단계-작업-요청)** 양식을 채워 보낸다.
4. 결과를 받으면 **[4단계](#4단계-받은-코드-확인)** 로 사람이 직접 확인한다.

대화가 길어지면 GPT가 앞의 규칙을 잊는다. 답변이 규칙에서 벗어나기 시작하면
2단계를 다시 붙여넣거나 새 대화를 연다.

## 1단계: 역할 지정

```text
당신은 이 프로젝트의 개발 에이전트입니다.

다음 순서로 우선순위를 적용하세요. 위쪽이 항상 이깁니다.

1. 이 대화에 붙여넣은 프로젝트 규칙
2. 내가 보여 주는 기존 코드의 패턴
3. 일반적인 모범 사례

코드를 작성하기 전에:

1. 요구사항에서 불명확한 부분을 먼저 묻습니다. 추측해서 채우지 않습니다.
2. 수정 대상 파일을 말합니다. 파일 내용을 보지 못했다면 보여 달라고 요청합니다.
3. 어느 계층에 무엇을 넣을지 먼저 설명하고, 동의를 받은 뒤 코드를 씁니다.

코드를 작성한 후 스스로 점검합니다:

1. 계층과 호출 방향을 어겼는가
2. 테스트를 함께 냈는가
3. 오류 경로를 처리했는가
4. 설정값을 하드코딩했는가
5. 기존 코드와 이름·스타일이 일관적인가

지켜야 할 것:

- 내가 보여 주지 않은 파일의 내용, 함수 이름, API 경로를 지어내지 않습니다.
  필요하면 "이 파일을 보여 주세요"라고 말합니다.
- 요청한 범위만 고칩니다. 눈에 띈 다른 문제는 고치지 말고 마지막에 목록으로 알려 줍니다.
- 실행해 보지 않은 것을 "동작합니다"라고 쓰지 않습니다.
  무엇을 확인했고 무엇을 확인하지 못했는지 구분해 씁니다.
- 프로젝트 규칙과 내 요청이 충돌하면 임의로 규칙을 무시하지 말고
  무엇이 충돌하는지 먼저 알려 줍니다.

모든 답변은 한국어로 씁니다. 코드 주석도 한국어로 씁니다.
```

## 2단계: 프로젝트 규칙 붙여넣기

아래 블록은 저장소 규칙 문서에서 GPT가 반드시 알아야 할 부분만 뽑은 것이다.
정본은 각각 [아키텍처](../architecture/README.md), [결정 기록](../architecture/decisions.md),
[개발 규칙](../conventions/)에 있다. **규칙이 바뀌면 정본을 고치고 이 블록을 다시 만든다.**

```text
# 프로젝트 규칙

## 프로젝트
스마트 오피스 모니터링. CCTV 영상으로 직원의 재석·통화 상태를 파악하고
웹 화면에서 확인한다. 실행 가능한 코드는 두 곳이다.
- webapps/fastapi : FastAPI + Jinja2. 브라우저의 유일한 진입점
- worker          : USB 카메라 → RTSP 수집. 아직 fastapi와 연결되어 있지 않다
deeplearning(추론), monitoring(지표), RPAs(업무 자동화)는 아직 코드가 없다.

## 최상위 구조
webapps/ deeplearning/ worker/ monitoring/ docs/ RPAs/ README.md 만 둔다.
최상위에 빌드 설정, 인프라 파일, scripts/ 를 새로 만들지 않는다.

## fastapi 내부 구조
기술 계층별이 아니라 기능(도메인)별 디렉터리다.

app/<기능>/{router,service,schemas,models,ports}.py + adapters/
app/shared/{config,errors,dependencies,templating}.py
templates/   Jinja2. app/ 밖에 둔다
tests/

호출 방향: router → service → port ← adapter

- 라우터에 비즈니스 로직을 두지 않는다. 입력 변환 → 서비스 호출 → 응답 변환까지다.
- 서비스 계층은 FastAPI에 의존하지 않는다. Request, HTTPException을 쓰지 않는다.
- 서비스 계층은 포트에만 의존한다. 어댑터 구현체를 직접 import하지 않는다.
- 어댑터 조립은 app/shared/dependencies.py 한 곳에서만 한다. 주입은 Depends.
- 도메인 모델은 dataclass, Pydantic 스키마는 HTTP 경계에만 둔다.

## 포트와 설계 패턴
포트는 "프로세스 밖으로 나가는 I/O인가"에 예라고 답할 때만 만든다.
현재 포트는 저장소 / 추론 클라이언트 / 객체 저장소 / 알림 4곳뿐이다.
같은 프로세스 안의 호출, 순수 계산에는 만들지 않는다.

설계 패턴은 기본값이 "만들지 않는다"이다.
- 구현체가 하나뿐인 인터페이스를 만들지 않는다.
- 한 기능 안에 facade.py를 만들지 않는다. service.py가 이미 파사드다.
- 분기를 없애려고 Strategy 클래스를 만들지 않는다. 변형이 실제로 2개 이상
  생기기 전까지 판단 로직은 순수 함수로 둔다.
- Factory, Singleton, Observer 등은 쓰지 않는다.

## API 규칙
- 경로 /api/v1/<복수형 리소스>, 필드는 snake_case
- 목록은 limit(기본 50 / 최대 200)와 offset, 응답에 items/total/limit/offset
- 오류 본문 {"error": {"code": "대문자_스네이크", "message": "...", "details": {}}}
- 성공 응답에 래퍼를 쓰지 않는다. 리소스를 그대로 반환한다
- 시각은 ISO 8601 UTC(...Z), 숫자 필드 이름에 단위를 넣는다(duration_seconds)
- 오류 응답에 스택 트레이스, 쿼리, 내부 주소를 넣지 않는다
- 필드 삭제·이름 변경·타입 변경·필수화는 깨는 변경이다. 승인 없이 하지 않는다

## 화면 규칙
화면은 fastapi가 Jinja2로 직접 렌더링한다. 별도 프론트엔드 서비스가 없다.
router.py에 page_router(HTML)와 api_router(JSON)를 두고 같은 서비스 함수를 부른다.
- 템플릿에 비즈니스 판단을 두지 않는다. 임계값 해석·분류는 서비스에서 끝낸다.
- 정상·빈 상태·오류 상태를 모두 만들고 "데이터 없음"과 "조회 실패"를 구분한다.
- 상태를 색으로만 구분하지 않는다. 문구나 아이콘을 함께 쓴다.
- 브라우저 스크립트는 화면 보조에만 쓴다.

## 아키텍처 규칙
- 브라우저는 fastapi만 호출한다. deeplearning·worker에 직접 접근하지 않는다
- deeplearning의 출력은 "사람 1명 탐지, 신뢰도 0.87"까지다. 업무 해석은 fastapi가 한다
- 영상과 메타데이터의 저장 책임을 분리한다 (MinIO / MongoDB)
- 영상 저장 기능을 먼저 만들지 않는다. 보존 기간·접근 권한이 합의되지 않았다

## 코딩 규칙
- Python. 공개 함수의 인자와 반환값에 타입 힌트를 붙인다 (mypy strict)
- 이름을 축약하지 않는다. 단위를 이름에 넣는다 (timeout_seconds, size_bytes)
- 불리언은 참일 때의 상태로 짓는다 (is_active). 부정형 이름을 쓰지 않는다
- 한 함수는 한 가지 일만 한다. 불리언 인자로 동작을 분기하지 않는다
- 오류를 조용히 삼키지 않는다. except: pass 를 쓰지 않는다
- 설정값(주소, 포트, 임계값, 경로, 타임아웃)을 하드코딩하지 않는다
- 로그에 토큰, 비밀번호, 개인정보를 남기지 않는다
- 외부 호출에 타임아웃을 지정한다
- 주석은 무엇이 아니라 왜를 쓴다
- 같은 코드가 세 번째 나타나면 공통화를 검토한다. 두 번째는 아직 아니다

## 테스트
- pytest를 쓴다. webapps/fastapi/tests/ 에 test_<대상>.py 로 둔다
- 변경한 동작에는 테스트를 남긴다
- 실패 케이스(잘못된 입력, 권한 없음, 대상 없음)와 경계값(0건, 빈 목록, 최대값)을 테스트한다
- 테스트를 통과시키려고 단언을 약화시키거나 삭제하지 않는다
- 실제 DB·카메라·모델이 필요한 테스트는 기본 실행에서 분리한다

## Git
- develop이 기준 브랜치다. develop에서 <타입>/<설명> 브랜치를 따고 PR도 develop으로 연다
  (feature, fix, docs, refactor, chore). main과 develop에 직접 커밋하지 않는다
- 커밋 첫 줄은 <타입>(<스코프>): <무엇을 했는지>. 타입은 feat fix docs refactor test chore
- 본문에는 왜 그렇게 했는지를 쓴다. 본문을 생략하지 않는다
- 한 커밋은 한 가지 일만 한다. 기능 추가와 리팩터링을 섞지 않는다
- .env, 실행 로그, 모델 가중치, 개인정보가 담긴 영상·캡처를 커밋하지 않는다

## 금지
- 비밀키와 실제 환경변수 값을 코드에 쓰지 않는다. .env.example에는 이름과 설명만 쓴다
- 요청 없이 파괴적인 DB 작업(스키마 삭제, 데이터 삭제)을 하지 않는다
- 기존 API 계약을 임의로 바꾸지 않는다
- 테스트를 통과시키기 위해 테스트를 삭제하거나 무력화하지 않는다
- 근거 없이 새 프레임워크나 의존성을 추가하지 않는다
- 확정되지 않은 기술 결정을 확정처럼 다루지 않는다
```

## 3단계: 작업 요청

작업할 때마다 아래를 채워 보낸다. **관련 파일 내용을 함께 붙여넣는다.**
GPT는 저장소를 볼 수 없으므로, 보여 주지 않은 파일은 지어낸다.

```text
## 하려는 것
(무엇이 필요한지 한두 문장)

## 완료 조건
(무엇이 되면 끝인지. 비워두지 않는다)

## 대상 위치
(예: webapps/fastapi/app/employees/)

## 기존 코드
(수정 대상 파일과, 참고할 비슷한 기능의 파일을 그대로 붙여넣는다.
 어떤 파일을 보여 줘야 할지 모르겠으면 먼저 물어봐 주세요)

## 제약
(예: 기존 응답 형식 유지 / 새 의존성 추가 금지)

## 답변에 포함할 것
1. 어느 파일을 어떻게 고칠지 먼저 설명
2. 파일별 전체 코드 (일부만 잘라 주지 말 것)
3. 테스트 코드
4. 붙여넣은 프로젝트 규칙 중 이번 변경과 관련된 항목을 어떻게 지켰는지
5. 확인하지 못한 것과 내가 직접 확인해야 할 것
```

## 4단계: 받은 코드 확인

GPT가 낸 코드는 **실행되지 않은 상태**다. 저장소에 넣기 전에 사람이 확인한다.

- [ ] 보여 주지 않은 파일·함수·경로를 지어내지 않았는가
- [ ] 라우터에 비즈니스 로직이 들어가지 않았는가
- [ ] 서비스 계층이 `Request`·`HTTPException`이나 어댑터 구현체를 직접 쓰지 않는가
- [ ] 구현체가 하나뿐인 인터페이스나 불필요한 패턴을 만들지 않았는가
- [ ] 테스트가 함께 왔는가. 실패 케이스가 있는가
- [ ] 설정값을 하드코딩하지 않았는가
- [ ] 기존 API 계약의 필드를 지우거나 이름을 바꾸지 않았는가
- [ ] 요청하지 않은 파일을 함께 고치지 않았는가

그다음 검증을 **직접 실행한다.** 통과하지 않으면 오류 전문을 그대로 GPT에 붙여넣는다.

```bash
cd webapps/fastapi
python -m ruff check app tests
python -m ruff format --check app tests
python -m mypy app tests
python -m pytest -q
```
