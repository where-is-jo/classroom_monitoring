# 문서 갱신 프롬프트

실제 코드와 설정을 기준으로 문서를 맞출 때 사용한다.

## 사용법

1. 아래 변수 값을 정한다. 갱신 범위를 좁게 잡을수록 결과가 정확하다.
2. `## 프롬프트` 블록을 복사해 변수를 치환한 뒤 에이전트에게 전달한다.

관련 문서: [AGENTS.md](../agents/AGENTS.md) · [문서 갱신 Skill](../skills/update-documentation/SKILL.md)

## 변수

| 변수 | 설명 | 예 |
| --- | --- | --- |
| `{{SCOPE}}` | 갱신 대상 범위 | `webapps/backend 문서 전체` |
| `{{TRIGGER}}` | 갱신이 필요해진 이유 | `이벤트 조회 API 추가` |
| `{{KNOWN_GAPS}}` | 이미 아는 불일치(없으면 `없음`) | |
| `{{DECIDED_ITEMS}}` | 확정된 미결정 항목(없으면 `없음`) | `저장소를 MongoDB로 확정` |

## 프롬프트

```text
아래 범위의 문서를 실제 코드·설정에 맞게 갱신한다.

## 작업 목적
문서를 늘리는 것이 아니라, 읽는 사람이 문서대로 따라 했을 때
실제와 어긋나지 않게 만드는 것이 목적이다.

## 입력 정보
- 갱신 범위: {{SCOPE}}
- 갱신이 필요해진 이유: {{TRIGGER}}
- 이미 아는 불일치: {{KNOWN_GAPS}}
- 확정된 미결정 항목: {{DECIDED_ITEMS}}

## 참고할 Agent
- `docs/agents/AGENTS.md` — 특히 Source of Truth 표에서 주제별 기준 문서를 확인한다
- `docs/agents/documentation-agent.md`

## 참고할 Skill
- `docs/skills/update-documentation/SKILL.md` — 절차를 그대로 따른다

## 작업 절차
1. 대상 문서의 서술을 하나씩 실제 코드·설정과 대조한다.
2. 확인할 수 없는 서술은 표시해 두고, 추측으로 메우지 않는다.
3. 같은 내용을 다루는 다른 문서가 있으면 기준 문서 하나로 모으고
   나머지는 링크로 바꾼다.
4. 새 문서를 만들기 전에 기존 문서 수정으로 해결되는지 판단한다.
5. 사실(현재 그렇다) / 결정(그렇게 하기로 했다) / 예정(아직 아니다)을 구분해 표기한다.
6. {{DECIDED_ITEMS}}가 있으면 해당 항목의 `결정 필요` 표기를 갱신하고,
   루트 `README.md`의 미결정 항목 목록도 함께 정리한다.
7. 상대 링크의 대상 파일이 존재하는지 확인한다.
8. 이 문서를 참조하던 다른 문서의 설명이 여전히 맞는지 확인한다.

## 금지 사항
- 코드를 확인하지 않고 동작을 설명하지 않는다.
- 존재하지 않는 명령·API·파일 경로를 적지 않는다.
- 실행해 보지 않은 명령을 문서에 남기지 않는다.
- 미확정 사항을 확정처럼 쓰지 않는다. `예정`, `후보`, `결정 필요`로 표시한다.
- 같은 내용을 여러 문서에 복사하지 않는다.
- 문서 정리를 이유로 코드를 수정하지 않는다. 코드 쪽 문제로 보이면 보고만 한다.
- 문서를 임의로 삭제하지 않는다. 참조하는 문서를 먼저 확인하고 통합안을 제시한다.
- 변경 날짜·작성자 서명을 추가하지 않는다. 이력은 Git이 관리한다.
- 내용이 없는 절을 만들어 분량을 채우지 않는다.

## 검증 방법
- 모든 상대 링크의 대상 파일이 존재하는지 확인한다.
- 문서에 남긴 실행 명령을 실제로 실행해 본다(실행 가능한 경우).
- 갱신한 서술의 근거가 된 코드 위치를 보고에 적는다.
- 중복이 실제로 제거되었는지 확인한다.

## 완료 보고 형식
## 작업 요약
## 발견한 불일치와 처리 결과
- 수정함 / 코드 쪽 문제로 보고함 / 확인 불가

## 생성 또는 변경한 파일
## 근거로 확인한 코드 위치
## 실행한 검증
## 실행하지 못한 검증
## 남은 위험 또는 후속 작업
```
