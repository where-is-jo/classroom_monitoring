# Pull Request 리뷰 프롬프트

병합 전 변경분을 검토할 때 사용한다.

## 사용법

1. 아래 변수 값을 정한다.
2. `## 프롬프트` 블록을 복사해 변수를 치환한 뒤 에이전트에게 전달한다.

관련 문서: [AGENTS.md](../agents/AGENTS.md) · [코드 리뷰 Skill](../skills/review-code/SKILL.md)

## 변수

| 변수 | 설명 | 예 |
| --- | --- | --- |
| `{{PR_REFERENCE}}` | PR 번호·URL 또는 브랜치 | `feature/event-list` |
| `{{CHANGE_INTENT}}` | 이 변경이 해결하려는 문제 | |
| `{{CHANGED_AREAS}}` | 변경된 영역 | `webapps/fastapi` |
| `{{AUTHOR_VALIDATION}}` | 작성자가 실행한 검증 | `단위 테스트 통과` |
| `{{FOCUS}}` | 특히 봐줬으면 하는 부분(없으면 `없음`) | |

## 프롬프트

```text
아래 변경분을 병합 전에 검토한다.

## 작업 목적
병합해도 되는지 판단한다. 취향 차이가 아니라 실제로 문제가 될 항목을
중요도 순으로 정리하는 것이 목적이다.

## 입력 정보
- 대상: {{PR_REFERENCE}}
- 변경 의도: {{CHANGE_INTENT}}
- 변경 영역: {{CHANGED_AREAS}}
- 작성자가 실행한 검증: {{AUTHOR_VALIDATION}}
- 중점 확인 요청: {{FOCUS}}

## 참고할 Agent
- `docs/agents/AGENTS.md` (공통 계약과 금지 사항)
- 변경 영역의 Agent 문서(fastapi / ai / rpa / documentation)
- 규칙 위반을 지적할 때는 근거가 되는 문서 경로를 함께 적는다.

## 참고할 Skill
- `docs/skills/review-code/SKILL.md` — 점검 순서와 출력 형식을 그대로 따른다

## 작업 절차
1. 변경 의도를 파악한다. 불명확하면 추측해서 지적하지 말고 먼저 묻는다.
2. 변경 전 코드가 어떻게 동작했는지 확인한다.
3. `docs/skills/review-code/SKILL.md`의 순서대로 점검한다.
   요구사항 → 오류 → 보안 → 데이터 손실 → 동시성 → 성능 → 테스트 → 문서
4. 각 지적에 재현 조건이나 근거를 붙인다.
5. 아키텍처 규칙 위반이 있는지 확인한다.
   - 템플릿이나 브라우저 스크립트에 비즈니스 판단이 들어갔는가
   - 라우터에 비즈니스 로직이 들어갔는가
   - 서비스 간 계약이 문서 없이 바뀌었는가
   - 영상과 메타데이터의 저장 책임이 섞였는가
6. 병합을 막는 항목과 그렇지 않은 항목을 나눈다.

## 금지 사항
- 코드를 직접 수정하지 않는다. 이 작업은 검토만 한다.
- 확신 없는 문제를 단정하지 않는다. 질문 형태로 남긴다.
- 규칙 문서에 근거가 없는 취향 문제를 병합 차단 항목에 넣지 않는다.
- 이번 변경과 무관한 기존 코드의 문제를 같은 항목에 섞지 않는다.
- 변경분을 실행하지 않았으면서 동작을 확인했다고 쓰지 않는다.
- 지적 개수를 늘리기 위한 형식적 코멘트를 만들지 않는다.

## 검증 방법
- 가능하면 변경분을 실제로 실행하거나 테스트를 돌려 확인한다.
- 지적한 문제 중 재현 가능한 것은 재현해 본다.
- 실행하지 않은 항목은 리뷰 결과에 그대로 밝힌다.

## 완료 보고 형식
## 병합 전 수정 필요
- [파일:줄] 문제 — 어떤 입력·상황에서 무엇이 잘못되는가

## 수정 권장
- [파일:줄] 문제와 이유

## 참고 의견
- 반영하지 않아도 병합 가능한 제안

## 규칙 위반
- 위반 내용과 근거 문서 경로

## 확인한 것 / 확인하지 못한 것
```
