# Create FastAPI Feature

## Purpose

FastAPI 백엔드에 새 엔드포인트를 추가할 때, 계약을 먼저 정하고
라우터와 비즈니스 로직을 분리한 상태로 구현하기 위한 절차다.

## When to Use

- 새 API 엔드포인트를 추가할 때
- 기존 엔드포인트에 필드나 동작을 추가할 때
- 백엔드가 새 내부 서비스를 호출해야 할 때

다음에는 사용하지 않는다.

- 응답 형식 변경 없이 내부 구현만 고칠 때
- 버그 수정 → `investigate-bug` 프롬프트를 사용한다

## Required Inputs

| 입력 | 설명 |
| --- | --- |
| 기능 목적 | 누가 무엇을 하기 위한 API인가 |
| 요청 명세 | 경로, 메서드, 경로·쿼리 파라미터, 본문 필드 |
| 응답 명세 | 성공 시 반환 필드와 타입 |
| 오류 케이스 | 실패 상황과 각각의 상태 코드 |
| 권한 | 누가 호출할 수 있는가 |
| 소비자 | 이 API를 사용할 클라이언트 |

명세가 비어 있으면 구현 전에 확정한다. 추측으로 채우지 않는다.

## Preconditions

- [`webapps/backend/README.md`](../../../webapps/backend/README.md)와 [backend-agent](../../agents/backend-agent.md)를 읽었다
- [API 규칙](../../conventions/api-convention.md)을 확인했다
- 기존 라우터·서비스·스키마 구조를 조사했다
- 유사한 엔드포인트가 있으면 그 패턴을 확인했다

## Procedure

1. **기존 구조 조사**
   - 기능 디렉터리 배치와 그 안의 `router` · `service` · `schemas` · `ports` · `adapters` 위치를 확인한다.
   - 같은 리소스를 다루는 엔드포인트가 있으면 경로 규칙과 응답 형태를 맞춘다.
   - **재사용할 수 있는 기존 포트와 어댑터가 있는지 먼저 본다.** 저장소·객체 저장소 접근은 대부분 이미 있다.

2. **API 계약 확정**
   - 경로, 메서드, 요청·응답 필드, 상태 코드, 오류 케이스를 표로 적는다.
   - 기존 계약을 바꾸는 부분이 있으면 여기서 멈추고 소비자 영향을 보고한다.

3. **스키마 정의**
   - 요청·응답 Pydantic 모델을 만든다.
   - 필수/선택, 기본값, 값 범위를 스키마에 명시한다. 검증을 라우터 본문에서 하지 않는다.

4. **포트 확인 또는 선언**
   - 필요한 외부 I/O(저장소, 객체 저장소, 추론 호출, 알림)를 정리한다.
   - 기존 포트로 해결되면 새로 만들지 않는다.
   - 새 포트가 필요하면 `ports.py`에 `Protocol`로 선언한다. 도메인 타입만 주고받고
     MongoDB 문서나 HTTP 응답 형태를 시그니처에 노출하지 않는다.
   - 프로세스 밖과 통신하지 않는 것은 포트로 만들지 않는다.

5. **서비스 계층 구현**
   - 비즈니스 로직을 서비스 함수로 작성한다.
   - **포트에만 의존한다.** 어댑터 구현체를 직접 import하지 않는다.
   - FastAPI 타입(`Request`, `HTTPException`)을 서비스 계층에서 사용하지 않는다.

6. **어댑터 구현과 조립**
   - 포트를 실제 기술로 구현한다. MongoDB·MinIO SDK는 어댑터 안에만 둔다.
   - 외부 호출에는 타임아웃을 지정한다.
   - 어댑터를 서비스에 연결하는 조립 코드는 `shared/`에 모은다.

7. **라우터 구현**
   - 라우터는 입력 변환 → 서비스 호출 → 응답 변환만 한다.
   - 서비스 계층의 예외를 상태 코드로 변환한다.

8. **오류 처리**
   - 각 오류 케이스가 의도한 상태 코드로 나오는지 확인한다.
   - 오류 응답에 스택 트레이스·쿼리·내부 주소를 넣지 않는다.

9. **테스트 작성**
   - 서비스 계층: 포트를 테스트 대역으로 대체한 단위 테스트. 실제 MongoDB·MinIO를 쓰지 않는다.
   - 라우터: 성공, 검증 실패, 권한 실패, 대상 없음 케이스의 API 테스트

10. **문서 갱신**
    - 서비스 README와 API 문서에 새 엔드포인트를 반영한다.

## Validation

실제로 실행한다.

- 단위 테스트와 API 테스트 실행
- 타입 검사·린트 실행
- 자동 생성 API 스키마(OpenAPI)에 의도한 필드가 나오는지 확인
- 오류 케이스별 상태 코드 확인

실행 명령은 백엔드 구현이 생긴 뒤 `webapps/backend/README.md`에 기록한다.
확인하지 않은 명령을 보고에 적지 않는다.

## Expected Output

- 라우터 함수
- 서비스 계층 함수
- 요청·응답 Pydantic 스키마
- 오류 처리 코드
- 단위 테스트 및 API 테스트
- 갱신된 API 문서와 서비스 README
- [완료 보고](../../agents/AGENTS.md#completion-report)

## Failure Handling

| 상황 | 대응 |
| --- | --- |
| 요청 명세가 불완전하다 | 구현하지 말고 빠진 항목을 질문한다 |
| 기존 계약을 깨야 한다 | 멈추고 영향 범위와 대안을 보고한다 |
| 필요한 데이터가 저장소에 없다 | 임의로 스키마를 바꾸지 말고 별도 작업으로 분리해 보고한다 |
| 테스트가 실패한다 | 테스트를 고치지 말고 원인을 조사한다. 테스트가 틀렸다는 근거가 있을 때만 테스트를 수정한다 |
| 포트를 만들지 판단이 안 선다 | 프로세스 밖과 통신하지 않으면 만들지 않는다. 구현체가 하나뿐이고 바뀔 가능성이 없어도 마찬가지다. [ADR-0002](../../architecture/decisions/ADR-0002-backend-layered-with-ports.md) 기준을 적용한다 |
| 추론 통신 방식·알림 채널이 미확정이다 | 포트만 선언하고 어댑터는 최소 구현으로 두되, 결정 필요 항목으로 보고한다 |
| 영상 저장이 필요해 보인다 | 보존 기간·접근 권한이 합의되기 전까지 구현하지 않는다. [ADR-0004](../../architecture/decisions/ADR-0004-object-storage-minio.md) 참고 |

## Completion Checklist

- [ ] API 계약을 먼저 문서화했다
- [ ] 기존 계약 변경 여부와 소비자 영향을 확인했다
- [ ] 요청·응답이 Pydantic 스키마로 정의되어 있다
- [ ] 라우터에 비즈니스 로직이 없다
- [ ] 서비스 계층이 FastAPI에 의존하지 않는다
- [ ] 서비스 계층이 포트에만 의존하고 어댑터를 직접 import하지 않는다
- [ ] 새로 만든 포트가 있다면 프로세스 외부 I/O 경계에 해당한다
- [ ] 오류 케이스마다 상태 코드가 정해져 있다
- [ ] 오류 응답에 내부 정보가 없다
- [ ] 외부 호출에 타임아웃이 있다
- [ ] 테스트를 실제로 실행했다
- [ ] API 문서와 README를 갱신했다
