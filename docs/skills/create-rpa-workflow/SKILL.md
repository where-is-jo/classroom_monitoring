# Create RPA Workflow

## Purpose

새 업무 자동화를 만들 때, 코드보다 먼저 업무·입출력·실패 조건을 확정하고
사람이 복구할 수 있는 형태로 구현하기 위한 절차다.

## When to Use

- 반복 사무 업무를 자동화하는 새 RPA 프로젝트를 시작할 때
- 기존 RPA에 새 업무 단계를 추가할 때

다음에는 사용하지 않는다.

- 상시 실행되는 서비스 기능 → `webapps`에 구현한다
- 일회성 데이터 처리 → 자동화로 만들지 않는다

## Required Inputs

| 입력 | 설명 |
| --- | --- |
| 대상 업무 | 지금 사람이 어떤 순서로 하고 있는가 |
| 수행 빈도 | 하루 몇 회, 언제 |
| 대상 시스템 | 접근할 사내·외부 시스템 |
| 필요한 권한 | 계정 종류와 권한 범위(값은 받지 않는다) |
| 처리량 | 1회 실행당 대상 건수 |
| 실패 시 영향 | 잘못 실행되면 무엇이 잘못되는가 |

## Preconditions

- [`RPAs/README.md`](../../../RPAs/README.md)와 [rpa-agent](../../agents/rpa-agent.md)를 읽었다
- [`RPAs/examples/README.md`](../../../RPAs/examples/README.md)의 권장 구조를 확인했다
- 대상 업무의 담당자와 확인 절차를 파악했다

## Procedure

1. **업무 분해**
   - 사람이 수행하는 순서를 그대로 단계별로 적는다.
   - 각 단계를 `자동화 가능` / `사람 확인 필요` / `자동화 부적합`으로 분류한다.
   - 판단이 필요한 단계(예외 처리, 승인)는 자동화하지 않는다.

2. **트리거·입력·출력 정의**
   - 트리거: 수동 / 일정 / 이벤트
   - 입력: 조회 조건, 입력 파일, 대상 목록
   - 출력: 생성 파일, 전송 결과, 갱신 레코드

3. **성공·실패 조건 정의**
   - 무엇이 확인되면 성공인지 적는다. "오류 없이 끝남"은 성공 조건이 아니다.
   - 부분 실패를 어떻게 처리할지 정한다.

4. **자격 증명 외부화**
   - 필요한 계정과 권한 범위를 문서에 적는다.
   - 값은 환경변수로 주입하고 `.env.example`에는 이름과 설명만 넣는다.

5. **중복 실행 방지 설계**
   - 처리 대상을 식별하는 키를 정한다.
   - 처리 이력을 남기고 실행 시작 시 확인한다.

6. **재시도와 수동 개입 지점 정의**
   - 자동 재시도: 네트워크 오류, 일시적 응답 지연
   - 재시도 금지: 되돌릴 수 없는 작업(발송, 승인, 삭제), 입력 오류, 권한 거부
   - 중단 후 사람에게 넘길 조건을 명시한다.

7. **프로젝트 생성과 README 작성**
   - `RPAs/<rpa-name>/`을 만들고 README를 **코드보다 먼저** 작성한다.

8. **구현**
   - 되돌릴 수 없는 단계를 마지막에 배치한다.
   - 실행 시작·종료·처리 건수·실패 원인을 로그로 남긴다.

9. **운영 로그 정리**
   - 로그 위치와 형식을 README에 적는다.
   - 로그에 자격 증명과 개인정보가 들어가지 않는지 확인한다.

## Validation

- 안전한 대상(테스트 계정·테스트 데이터)으로 실행한다.
- 같은 입력으로 두 번 실행해 중복 처리가 없는지 확인한다.
- 실패를 의도적으로 만들어(잘못된 입력, 연결 차단) 중단과 로그를 확인한다.
- 로그 파일에 자격 증명·개인정보가 없는지 확인한다.
- **검증을 어떤 대상에서 했는지(테스트/운영) 보고에 반드시 밝힌다.**

운영 데이터로 시험 실행하지 않는다. 불가피하면 사전 승인을 받고 범위를 최소화한다.

## Expected Output

- `RPAs/<rpa-name>/README.md`
- 자동화 실행 코드
- `.env.example`(값 제외)
- 처리 이력·로그 기록
- [완료 보고](../../agents/AGENTS.md#completion-report) — 검증 조건 포함

## Failure Handling

| 상황 | 대응 |
| --- | --- |
| 업무 순서가 사람마다 다르다 | 자동화 전에 표준 순서를 확정한다 |
| 판단이 필요한 단계가 있다 | 자동화하지 말고 중단·보고 지점으로 둔다 |
| 자격 증명을 코드에 넣어야 할 것 같다 | 넣지 않는다. 주입 방법을 확정할 때까지 중단하고 보고한다 |
| 대상 시스템 화면이 자주 바뀐다 | 취약점으로 기록하고, 실패 시 조용히 넘어가지 않게 만든다 |
| 중복 실행 판별 키가 없다 | 임의 키를 만들지 말고 담당자와 확정한다 |
| 테스트 환경이 없다 | 운영에서 강행하지 말고 확인 후 진행한다 |

## Completion Checklist

- [ ] 업무 단계를 자동화 가능/사람 확인/부적합으로 분류했다
- [ ] 트리거·입력·출력이 문서화되어 있다
- [ ] 성공 조건과 실패 조건이 구체적이다
- [ ] 자격 증명이 코드·설정·로그에 없다
- [ ] 같은 입력으로 재실행해도 안전하다
- [ ] 중복 실행 방지 기준이 구현되어 있다
- [ ] 자동 재시도 대상과 금지 대상이 구분되어 있다
- [ ] 사람 확인 지점에서 중단하고 보고한다
- [ ] 로그에 개인정보가 없고 커밋 대상에서 제외되어 있다
- [ ] 검증 대상(테스트/운영)을 보고에 밝혔다
