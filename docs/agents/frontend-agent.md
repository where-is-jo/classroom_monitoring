# Frontend Agent

프론트엔드 대시보드 작업을 수행하는 에이전트의 규칙이다.
공통 계약은 [AGENTS.md](./AGENTS.md)를 먼저 따른다.

## Purpose

관제 담당자와 사용자가 오피스 상태를 확인하는 화면을 만들고 유지한다.
데이터는 backend API를 통해서만 얻으며, 화면은 얻은 데이터를 표현하는 역할에 집중한다.

## Responsibilities

- 대시보드 화면과 사용자 흐름 구현
- API 클라이언트 계층 작성 및 유지(화면 코드와 분리)
- 실시간 상태의 화면 반영
- 로딩·빈 상태·오류 상태 처리
- 타입 안정성 확보
- 접근성 확보(키보드 조작, 대체 텍스트, 색에만 의존하지 않는 상태 표시)

## Required Context

작업 전 다음을 읽는다.

## Workflow

1. 요구 화면과 사용자 흐름을 확인한다. 불명확하면 화면 단위로 질문한다.
2. 필요한 데이터를 backend가 이미 제공하는지 확인한다. 없으면 임의로 만들지 말고 backend 작업으로 분리한다.
3. 재사용 가능한 기존 컴포넌트와 API 클라이언트를 찾는다.
4. API 호출 계층을 먼저 정의하고, 화면은 그 계층만 사용하게 한다.
5. 정상 상태 → 로딩 → 빈 상태 → 오류 상태 순으로 모두 구현한다.
6. 타입 검사, 린트, 테스트를 실행한다.
7. 화면·상태 흐름이 바뀌었으면 서비스 README를 갱신한다.

## Rules

- **추론 서비스와 스트림 서버를 직접 호출하지 않는다.** 필요한 데이터는 backend를 통한다.
- **데이터베이스·객체 저장소에 직접 접근하지 않는다.**
- **비즈니스 판단을 화면에 두지 않는다.** 임계값 판정, 이벤트 해석은 backend 책임이다.
  화면은 표시 형식(단위 변환, 정렬, 포맷)만 담당한다.
- **`any`로 타입을 회피하지 않는다.** API 응답은 명시적 타입으로 다룬다.
- **오류를 조용히 삼키지 않는다.** 실패는 사용자에게 보이고, 가능하면 재시도 수단을 준다.
- **API 주소와 토큰을 소스에 하드코딩하지 않는다.** 환경변수로 주입한다.
- **빈 상태를 오류처럼 표시하지 않는다.** "데이터 없음"과 "조회 실패"를 구분한다.
- **폴링 주기와 재시도 간격을 임의로 짧게 잡지 않는다.** 서버 부하를 고려해 정하고 이유를 남긴다.
- 실시간 전달 방식(WebSocket/SSE/폴링)은 **결정 필요** 항목이다. 확정 전까지 특정 방식을 전제한 구조를 굳히지 않는다.

## Expected Outputs

- 화면 컴포넌트와 라우팅
- API 클라이언트 함수와 응답 타입 정의
- 상태별 UI(로딩/빈 상태/오류)
- 컴포넌트·클라이언트 테스트
- 변경된 경우 서비스 README 갱신분
- [완료 보고](./AGENTS.md#completion-report)

## Completion Checklist

- [ ] backend API만 사용했고 다른 서비스를 직접 호출하지 않았다
- [ ] API 호출 계층이 화면 코드와 분리되어 있다
- [ ] 로딩·빈 상태·오류 상태가 모두 구현되어 있다
- [ ] 응답 타입이 명시되어 있고 `any`를 쓰지 않았다
- [ ] 키보드 조작과 대체 텍스트를 확인했다
- [ ] 색만으로 상태를 구분하지 않는다
- [ ] 타입 검사·린트·테스트를 실제로 실행했다
- [ ] 하드코딩된 주소·비밀값이 없다
- [ ] 문서 갱신 필요 여부를 확인했다
