# 테스트

**목적**: 무엇을 어느 수준에서 테스트할지 공통 기준을 정한다.
**대상 독자**: 코드를 작성하거나 리뷰하는 팀원.

> **실행 명령의 정본은 각 서비스 README다.** 이 문서에 복사하지 않는다.
> 새 서비스에 도구를 도입한 사람이 해당 서비스 README에 실행 명령을 기록한다.

코드를 쓸 때 지킬 개별 규칙은 [코딩 규칙](../conventions/coding-convention.md#테스트)에 있다.
이 문서는 **어떤 테스트를 어디에 둘지**를 다룬다.

## 테스트 수준

| 수준 | 대상 | 외부 의존 | 실행 빈도 |
| --- | --- | --- | --- |
| 단위 | 함수, 클래스, 순수 로직 | 없음 | 항상 |
| 통합 | 여러 계층을 묶은 경로(API 요청 → 응답) | 대역으로 대체 | 항상 |
| 외부 의존 | 실제 DB·장비·모델이 필요한 검증 | 실물 | 분리 실행 |

**기본 실행에 포함되는 것은 앞의 두 수준까지다.**
실제 카메라, GPU, 모델 가중치, 운영 저장소를 요구하는 테스트는 별도로 표시해
기본 테스트에서 분리한다. 그렇지 않으면 아무도 테스트를 돌리지 않게 된다.

## 서비스별로 무엇을 테스트하나

각 서비스의 테스트 전략은 서비스 README에 있다. 요약하면 다음과 같다.

| 서비스 | 반드시 테스트할 것 | 분리할 것 |
| --- | --- | --- |
| [fastapi](../../webapps/fastapi/README.md) | 서비스 계층 로직, 요청 검증, 오류 상태 코드, 템플릿 렌더링 | 실제 저장소 연동 |
| [deeplearning](../../deeplearning/README.md) | 전처리·후처리, 결과 스키마 변환 | 실제 모델 추론 |
| [worker](../../worker/README.md) | 연결 상태 전이, 프레임 샘플링 로직 | 실제 카메라 연결 |
| [monitoring](../../monitoring/README.md) | 설정 파일 문법, 알림 규칙 표현식 | 실제 수집 |
| RPA | 입력 파싱, 중복 판별, 재시도 분기 | 실제 업무 시스템 접근 |

## 무엇을 테스트할지 고르기

- **실패 케이스를 테스트한다.** 성공 경로만 검증하는 테스트는 절반만 한 것이다.
  잘못된 입력, 권한 없음, 대상 없음, 외부 서비스 실패를 확인한다.
- **경계값을 테스트한다.** 0건, 빈 목록, `null`, 최대값.
- **버그를 고치면 회귀 테스트를 남긴다.** 수정 전에는 실패하고 수정 후에는 통과해야 한다.
  실제로 그런지 수정을 되돌려 확인한다.
- 프레임워크나 라이브러리 자체의 동작을 테스트하지 않는다.
- 커버리지 숫자를 목표로 삼지 않는다. 의미 없는 테스트가 늘어난다.

## 외부 의존 다루기

- 네트워크 호출, 저장소 접근, 파일 시스템, 현재 시각은 테스트에서 고정한다.
- 시간에 의존하는 로직은 시각을 주입받게 만든다. `sleep`으로 타이밍을 맞추지 않는다.
- 테스트마다 상태를 초기화한다. 실행 순서에 따라 결과가 달라지면 안 된다.
- 대역 데이터에 실제 개인정보와 영상을 쓰지 않는다.

## 테스트를 고치고 싶을 때

**테스트가 실패하면 먼저 코드를 의심한다.**

- 통과시키려고 단언을 약화시키거나 테스트를 삭제하지 않는다.
- 테스트가 틀렸다는 **근거**가 있을 때만 테스트를 고치고, 그 근거를 PR에 적는다.
- 간헐적으로 실패하는 테스트를 그대로 두지 않는다. 원인을 찾거나 분리한다.
  방치하면 실패 알림 전체가 무시된다.

## 현재 도구

`webapps/fastapi`는 **pytest**를 쓴다. 다른 서비스는 아직 코드가 없다.

| 항목 | 내용 |
| --- | --- |
| 도구 | pytest (+ FastAPI `TestClient`) |
| 위치 | `webapps/fastapi/tests/` |
| 이름 규칙 | `test_<대상>.py`, 함수는 `test_`로 시작 |
| 공통 픽스처 | `tests/conftest.py` — 포트의 테스트 대역을 제공 |
| 실행 | `cd webapps/fastapi && python -m pytest` |

pytest는 되돌리기 쉬운 선택이라 ADR을 쓰지 않았다.

### 린트와 타입 검사

테스트만으로는 규칙 준수를 확인할 수 없어 도구를 함께 둔다.

| 항목 | 내용 |
| --- | --- |
| 린트·포매터 | ruff — flake8·black·isort를 하나로 대체한다 |
| 타입 검사 | mypy `strict` |
| 설정 | [`webapps/fastapi/pyproject.toml`](../../webapps/fastapi/pyproject.toml) |
| 실행 | [fastapi README의 린트와 타입 검사](../../webapps/fastapi/README.md#린트와-타입-검사) |

ruff와 mypy도 pytest와 같은 이유로 ADR을 쓰지 않았다. 되돌리기 쉬운 선택이고,
[결정 기록의 대상](../architecture/decisions/README.md#언제-쓰는가)이 아니다.

**mypy는 처음부터 `strict`로 시작했다.** 코드가 작을 때가 가장 싸고,
나중에 소급 적용하면 고칠 곳이 파일 수에 비례해 늘어난다.

MongoDB 통합 테스트는 `mongodb` marker로 기본 실행에서 분리돼 있다. 실행 조건과
`TEST_DATABASE_URL` 안전 제약은 [fastapi README의 검증](../../webapps/fastapi/README.md#검증)을
따른다.

## 새 서비스에 도구를 도입할 때

`deeplearning`, `worker` 등에 처음 테스트를 넣는 사람은 다음을 함께 남긴다.

- [ ] 선택한 도구와 이유(되돌리기 어려우면 [ADR](../architecture/decisions/README.md))
- [ ] 테스트 파일 위치와 이름 규칙
- [ ] 실행 명령 — **실제로 실행해 확인한 것**
- [ ] 기본 실행과 분리 실행을 구분하는 방법
- [ ] 서비스 README의 테스트 전략 절 갱신
