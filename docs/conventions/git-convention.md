# Git 규칙

**목적**: 브랜치와 커밋을 다루는 최소한의 공통 규칙을 정한다.
**대상 독자**: 이 저장소에 커밋하는 모든 사람과 AI 에이전트.

복잡한 Git Flow는 쓰지 않는다. `main`에서 브랜치를 따고, 작업이 끝나면
Pull Request로 돌아온다. 그 이상은 필요해질 때 도입한다.

## 브랜치

`main`이 기준 브랜치다. `main`에 직접 커밋하지 않는다.

```text
<타입>/<간단한-설명>
```

| 타입 | 용도 |
| --- | --- |
| `feature` | 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서만 변경 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `chore` | 설정, 빌드, 의존성 |

- 소문자와 하이픈을 쓴다: `feature/event-list-api`
- 이슈 번호가 있으면 뒤에 붙여도 된다: `fix/stream-reconnect-42`
- 작업이 끝난 브랜치는 병합 후 삭제한다.

## 커밋 메시지

```text
<타입>: <무엇을 했는지 한 줄>

<필요하면 왜 그렇게 했는지>
```

- 첫 줄은 50자 내외로 줄인다. 마침표를 붙이지 않는다.
- **무엇을 했는지는 코드에 보인다. 본문에는 왜 했는지를 쓴다.**
- 한국어로 써도 되고 영어로 써도 된다. 한 커밋 안에서 섞지 않는다.

```text
fix: 스트림 재연결 시 이전 연결이 정리되지 않던 문제 수정

재연결마다 소켓이 쌓여 파일 디스크립터가 고갈됐다.
연결 교체 전에 기존 연결을 명시적으로 닫는다.
```

다음은 쓰지 않는다.

- `수정`, `update`, `작업중`, `wip` — 무엇을 했는지 알 수 없다
- 여러 작업을 뭉친 커밋 — 나눈다

## 변경 단위

**한 커밋은 한 가지 일만 한다.** 한 PR은 하나의 목적만 갖는다.

기능 추가와 리팩터링을 같은 커밋에 넣지 않는다. 리뷰어가 어느 변경이
동작에 영향을 주는지 구분할 수 없기 때문이다. 자동 포매터가 관련 없는 파일을
건드렸다면 그것만 따로 커밋한다.

작업 중 다른 문제를 발견하면 고치지 말고 기록해 둔다.
[구현 프롬프트](../prompts/implement-feature.md)의 금지 사항과 같은 이유다.

## Pull Request

제목은 커밋 메시지와 같은 형식으로 쓴다. 본문에는 다음을 넣는다.

- 무엇을 왜 바꿨는지
- 확인이 필요한 부분
- 실행한 검증과 그 결과
- 실행하지 못한 검증

리뷰는 [PR 리뷰 프롬프트](../prompts/review-pull-request.md)와
`review-code` 스킬을 사용한다.

- PR이 커지면 리뷰 품질이 떨어진다. 나눌 수 있으면 나눈다.
- 리뷰 지적에 대응한 커밋을 squash하지 않고 남겨두면 리뷰어가 확인하기 쉽다.
- 통과하지 않는 테스트를 둔 채 병합하지 않는다.

## 커밋하지 않는 것

**비밀정보를 절대 커밋하지 않는다.**

- 계정, 비밀번호, API 키, 토큰, 인증서
- 실제 값이 담긴 `.env`
- 개인정보가 포함된 데이터·영상·스크린샷
- 실행 로그, 대용량 모델 가중치, 빌드 산출물

`.env.example`에는 변수 이름과 설명만 넣는다.
자세한 내용은 [환경변수 규칙](./environment-convention.md)에 있다.

**이미 커밋했다면 해당 자격 증명을 먼저 폐기한다.**
이력에서 지우는 것만으로는 유출이 되돌려지지 않는다.
파일만 지우고 넘어가지 말고 팀에 알린다.
