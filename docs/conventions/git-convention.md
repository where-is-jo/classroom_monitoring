# Git 규칙

**목적**: 브랜치와 커밋을 다루는 최소한의 공통 규칙을 정한다.
**대상 독자**: 이 저장소에 커밋하는 모든 사람과 AI 에이전트.

복잡한 Git Flow는 쓰지 않는다. `develop`에서 브랜치를 따고, 작업이 끝나면
Pull Request로 돌아온다. 그 이상은 필요해질 때 도입한다.

## 브랜치

**`develop`이 기준 브랜치다.** 작업 브랜치는 `develop`에서 따고, Pull Request도
`develop`으로 연다. `main`에는 배포하는 시점에만 `develop`을 병합한다.

`main`과 `develop` 어느 쪽에도 직접 커밋하지 않는다.

| 브랜치 | 역할 |
| --- | --- |
| `main` | 배포된 상태. `develop`에서만 병합해 들어온다 |
| `develop` | 통합 기준. 작업 브랜치의 분기점이자 PR 대상 |
| `<타입>/<간단한-설명>` | 실제 작업 |

```text
<타입>/<간단한-설명>
```

| 타입 | 용도 |
| --- | --- |
| `feature` | 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서만 변경 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `chore` | 설정, 빌드, 의존성 |

- 소문자와 하이픈을 쓴다: `feature/event-list-api`
- 이슈 번호가 있으면 뒤에 붙여도 된다: `fix/stream-reconnect-42`
- 작업이 끝난 브랜치는 병합 후 삭제한다.

## 커밋 메시지

```text
<타입>(<스코프>): <무엇을 했는지 한 줄>

<왜 그렇게 했는지>

<필요하면 트레일러>
```

### 타입

| 타입 | 용도 |
| --- | --- |
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서만 변경 |
| `refactor` | 동작 변경 없는 구조 개선 |
| `test` | 테스트 추가·수정 |
| `chore` | 설정, 의존성, 저장소 관리 |

**목록에 없는 타입을 쓰지 않는다.** `perf`, `ci`, `style`, `build`, `revert`는
쓰지 않는다. 성능 개선은 `fix` 또는 `refactor`로, 의존성 변경은 `chore`로 쓴다.
포매터와 CI를 도입하면 그때 이 표에 추가한다.

커밋 타입 `feat`와 브랜치 타입 `feature`가 다른 것은 의도된 차이다. 관례를 따랐다.

### 스코프

**스코프는 선택이다.** 변경 영역이 하나로 분명할 때만 쓰고,
여러 영역에 걸치면 생략한다.

| 구분 | 값 |
| --- | --- |
| 서비스 | `fastapi`, `deeplearning`, `worker`, `monitoring`, `rpa` |
| fastapi 기능 | `students`, `classrooms`, `face-enrollment`, `student-monitoring`, `video-monitoring` |
| worker 단계 | `stream`, `inference`, `recorder` |
| 문서 영역 | `docs`, `agents` |
| 저장소 설정 | `config` |

목록에 없는 스코프가 필요하면 억지로 만들지 말고 생략한다.
새 서비스나 기능이 생기면 이 표에 추가한다.

### 작성 규칙

- 첫 줄은 50자 내외로 줄인다. 마침표를 붙이지 않는다.
- **무엇을 했는지는 코드에 보인다. 본문에는 왜 했는지를 쓴다.** 본문을 생략하지 않는다.
- 한국어로 써도 되고 영어로 써도 된다. 한 커밋 안에서 섞지 않는다.
- 한국어 제목은 "~추가", "~수정", "~제거"처럼 서술형으로 쓴다.
- AI 에이전트가 커밋하면 `Co-Authored-By` 트레일러를 붙인다.

```text
fix(worker): 스트림 재연결 시 이전 연결이 정리되지 않던 문제 수정

재연결마다 소켓이 쌓여 파일 디스크립터가 고갈됐다.
연결 교체 전에 기존 연결을 명시적으로 닫는다.

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

다음은 쓰지 않는다.

- `수정`, `update`, `작업중`, `wip` — 무엇을 했는지 알 수 없다
- 여러 작업을 뭉친 커밋 — 나눈다
- 본문 없이 제목만 있는 커밋 — 왜 했는지가 남지 않는다

## 변경 단위

**한 커밋은 한 가지 일만 한다.** 한 PR은 하나의 목적만 갖는다.

기능 추가와 리팩터링을 같은 커밋에 넣지 않는다. 리뷰어가 어느 변경이
동작에 영향을 주는지 구분할 수 없기 때문이다. 자동 포매터가 관련 없는 파일을
건드렸다면 그것만 따로 커밋한다.

작업 중 다른 문제를 발견하면 고치지 말고 기록해 둔다.
[구현 프롬프트](../prompts/implement-feature.md)의 금지 사항과 같은 이유다.

## Pull Request

제목은 커밋 메시지와 같은 형식으로 쓴다. 본문에는 다음을 넣는다.

- 무엇을 왜 바꿨는지
- 확인이 필요한 부분
- 실행한 검증과 그 결과
- 실행하지 못한 검증

리뷰는 [PR 리뷰 프롬프트](../prompts/review-pull-request.md)와
`review-code` 스킬을 사용한다.

- PR이 커지면 리뷰 품질이 떨어진다. 나눌 수 있으면 나눈다.
- 리뷰 지적에 대응한 커밋을 squash하지 않고 남겨두면 리뷰어가 확인하기 쉽다.
- 통과하지 않는 테스트를 둔 채 병합하지 않는다.

## 커밋하지 않는 것

**비밀정보를 절대 커밋하지 않는다.**

- 계정, 비밀번호, API 키, 토큰, 인증서
- 실제 값이 담긴 `.env`
- **학생 얼굴이 담긴 영상·이미지·화면 캡처**, 얼굴 embedding 파일
- 개인정보가 포함된 데이터·영상·스크린샷
- 실행 로그, 대용량 모델 가중치, 빌드 산출물

수집한 영상과 프레임은 `worker/**/data/` 아래에 쌓이며 `.gitignore` 대상이다.
얼굴이 담기므로 어떤 경우에도 커밋하지 않는다.

`.env.example`에는 변수 이름과 설명만 넣는다.
자세한 내용은 [환경변수 규칙](./environment-convention.md)에 있다.

**이미 커밋했다면 해당 자격 증명을 먼저 폐기한다.**
이력에서 지우는 것만으로는 유출이 되돌려지지 않는다.
파일만 지우고 넘어가지 말고 팀에 알린다.
