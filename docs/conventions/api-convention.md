# API 규칙

**목적**: fastapi가 제공하는 HTTP API의 형태를 통일한다.
**대상 독자**: API를 만드는 사람과 소비하는 사람, AI 에이전트.

> 아직 구현된 엔드포인트가 없다. 이 문서는 첫 엔드포인트를 만들 때 적용할 기준이다.
> 여기서 정하지 않은 것은 첫 구현 시 결정하고 이 문서에 반영한다.

## URL과 리소스 이름

- 리소스는 **복수형 명사**를 쓴다: `/events`, `/cameras`
- 소문자와 하이픈을 쓴다: `/stream-sessions`
- URL에 동사를 넣지 않는다. 동작은 HTTP 메서드로 표현한다.
  - `POST /events/create` (X) → `POST /events` (O)
- 계층은 두 단계까지만 쓴다: `/cameras/{camera_id}/events`
  더 깊어지면 쿼리 파라미터로 푼다.
- 상태 변경처럼 CRUD로 표현하기 어려운 동작은 하위 리소스로 만든다:
  `POST /stream-sessions/{id}/reconnect`

## 메서드

| 메서드 | 용도 | 같은 요청을 반복해도 안전한가 |
| --- | --- | --- |
| `GET` | 조회 | 예 |
| `POST` | 생성, 그 외 동작 | 아니오 |
| `PUT` | 전체 교체 | 예 |
| `PATCH` | 부분 수정 | 아니오 |
| `DELETE` | 삭제 | 예 |

`GET`은 상태를 바꾸지 않는다. 예외를 두지 않는다.

## 요청과 응답 스키마

- 모든 요청·응답을 Pydantic 모델로 정의한다. 원시 dict를 반환하지 않는다.
- 필드 이름은 `snake_case`를 쓴다.
- 시각은 ISO 8601 UTC 문자열로 주고받는다: `2026-08-05T09:00:00Z`
- 숫자 필드 이름에 단위를 넣는다: `duration_seconds`, `size_bytes`
- 값이 없음을 나타낼 때 `null`과 빈 문자열을 섞어 쓰지 않는다. `null`로 통일한다.

**응답 래퍼를 강제하지 않는다.** 모든 응답을 `{"data": ..., "error": ...}`로 감싸는
방식은 이 프로젝트에서 채택하지 않았다. 리소스를 그대로 반환하고, 오류는 상태 코드와
오류 본문으로 표현한다. 래퍼가 필요하다는 근거가 생기면 [결정 기록](../architecture/decisions.md)에 남긴 뒤 도입한다.

## 상태 코드

| 코드 | 사용 시점 |
| --- | --- |
| `200` | 조회·수정 성공 |
| `201` | 생성 성공. `Location` 헤더에 생성된 리소스 경로를 넣는다 |
| `204` | 성공했고 본문이 없다(주로 삭제) |
| `400` | 요청 형식·값이 잘못됨 |
| `401` | 인증되지 않음 |
| `403` | 인증됐지만 권한 없음 |
| `404` | 대상이 없음 |
| `409` | 현재 상태와 충돌(중복 생성 등) |
| `422` | 스키마 검증 실패(FastAPI 기본) |
| `500` | 서버 내부 오류 |
| `503` | 의존 서비스 사용 불가 |

- **실패를 `200`으로 돌려주지 않는다.** 본문에 `"success": false`를 넣는 방식을 쓰지 않는다.
- 권한이 없는 리소스의 존재 자체를 숨겨야 한다면 `404`를 쓴다. 그 판단은 리소스별로 정한다.

## 오류 응답

오류 본문은 다음 형태를 사용한다.

```json
{
  "error": {
    "code": "CAMERA_NOT_FOUND",
    "message": "요청한 카메라를 찾을 수 없습니다.",
    "details": {}
  }
}
```

- `code`: 클라이언트가 분기할 수 있는 고정 식별자. 대문자 스네이크. 메시지를 파싱하게 만들지 않는다.
- `message`: 사람이 읽는 설명. 사용자에게 그대로 보여줄 수 있는 수준으로 쓴다.
- `details`: 필드별 오류 등 부가 정보. 없으면 생략한다.

**오류 본문에 내부 정보를 넣지 않는다.** 스택 트레이스, 쿼리문, 내부 호스트 주소,
파일 경로는 로그로만 남긴다.

## 페이지네이션

목록 조회는 처음부터 페이지네이션을 넣는다. 나중에 추가하면 계약이 깨진다.

```text
GET /events?limit=50&offset=0
```

- `limit`: 기본 50, 최대 200. 상한을 두지 않으면 전체 조회 요청이 들어온다.
- `offset`: 기본 0
- 응답에 전체 건수를 포함한다.

```json
{
  "items": [],
  "total": 0,
  "limit": 50,
  "offset": 0
}
```

이벤트처럼 계속 쌓이고 실시간으로 늘어나는 목록은 offset 방식에서 항목이
밀리거나 중복될 수 있다. 커서 기반으로 바꿀지는 **결정 필요** 항목이다.

## 정렬과 필터

- 정렬: `?sort=created_at&order=desc`
- 필터는 필드 이름을 그대로 쓴다: `?camera_id=cam-01&status=active`
- 기간 조회: `?from=...&to=...` (ISO 8601, `from` 포함, `to` 미포함)

## 버전 정책

경로에 버전을 넣는다: `/api/v1/events`

- 첫 릴리스는 `v1`이다.
- 버전은 **하위 호환을 깨야 할 때만** 올린다. 필드 추가는 버전을 올릴 이유가 아니다.
- 새 버전을 내면 이전 버전의 지원 종료 시점을 함께 공지한다.

## 하위 호환성

다음은 **깨는 변경**이다. 승인 없이 하지 않는다.

- 필드 삭제, 이름 변경, 타입 변경
- 선택 필드를 필수로 바꾸기
- 값의 의미 변경(같은 필드에 다른 뜻을 담기)
- 상태 코드 변경
- 기본값 변경

다음은 **깨지 않는 변경**이다.

- 선택 필드 추가
- 새 엔드포인트 추가
- 응답에 새 필드 추가(클라이언트가 모르는 필드를 무시한다는 전제)

깨는 변경이 필요하면 새 필드를 추가하고 이전 필드를 한동안 함께 유지한 뒤 제거한다.
