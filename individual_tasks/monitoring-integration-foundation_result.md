# 무엇을 왜 했나

모델 담당자가 얼굴 식별 결과를 연결하기 전에 필요한 강의실·학생·좌석·카메라·ROI·탐지 이벤트·학생 상태·SSE 경계를 정리하고 구현했다. 목표는 worker가 모델 추론 결과만 전달하면 FastAPI가 영속 데이터와 연결해 학생의 좌석 상태를 판정하고, 실시간 모니터링 화면과 강의실 좌석 현황 대시보드에 같은 상태를 전달하도록 만드는 것이었다.

작업은 `feature/monitoring-integration-foundation` 브랜치에서 진행했다. 현재 브랜치는 최신 `develop`을 조상으로 가지며, PR1 위에 쌓였다는 이전 설명은 더 이상 유효하지 않다.

구현 이후 실제 노트북 웹캠, MongoDB, MediaMTX, YOLO worker를 이용한 로컬 수용 테스트도 수행했다. 테스트 목적은 모델 식별 전 단계의 연결이 실제 실행 환경에서도 이어지는지 확인하고, 다음 작업자가 해결해야 할 통합 공백을 찾는 것이었다.

# 무엇이 바뀌었나

## 구현과 계약

- 카메라가 존재하는 강의실만 참조하도록 무결성 검사를 보강했다.
- 카메라별 좌석 ROI를 학생·좌석과 연결하고 MongoDB에 저장하는 흐름을 추가했다.
- 최근 탐지 이벤트를 바탕으로 학생 상태를 조회하는 서비스를 구현했다.
- 학생 상태 SSE 스트림을 추가하고 실시간 모니터링 화면과 강의실 좌석 현황 화면이 상태 변경을 반영하도록 연결했다.
- worker 이벤트 계약에 선택적인 `student_id`, `identity_confidence`, `face_bbox`를 추가했다.
- 모델과 worker의 책임은 `worker/inference/MODEL_INTEGRATION.md`에 정리했다. 모델은 식별 결과만 제공하고, 학생 이름·학번·강의실·좌석·최종 상태는 FastAPI가 결정한다.
- 식별 정보는 `student_id`와 `identity_confidence`를 함께 제공해야 하며, 모르는 얼굴을 가장 가까운 학생으로 추정하지 않는다.
- 재시도 시 동일한 `event_id`를 유지해 중복 이벤트를 멱등 처리한다.

## 실제 웹캠 수용 테스트에서 확인한 동작

- MongoDB 모드의 FastAPI를 재시작한 뒤에도 테스트 강의실, 학생, 좌석, 좌석 지정 정보가 유지됐다.
- 노트북 웹캠 영상을 FFmpeg로 MediaMTX에 게시하고, OpenCV 기반 worker가 스트림에 연결해 YOLO 추론 루프와 탐지 이벤트 전송을 실행했다.
- ROI 연결 화면에서 WebRTC 영상을 재생하고, 사각형 ROI를 학생과 좌석에 연결해 MongoDB에 저장했다.
- 실시간 모니터링 화면은 WebRTC 영상과 탐지 SSE를 함께 수신했다.
- 식별된 사람 이벤트를 계약대로 전송했을 때 학생 상태 API가 `PRESENT`를 반환했고, 이미 열려 있던 강의실 좌석 현황 화면도 새로고침 없이 `확인 필요`에서 `재석`으로 바뀌었다.
- 중복 이벤트는 기존 계약대로 멱등 처리됐다.

## 테스트 중 발견한 통합 공백

- 실제 웹캠 영상이 거의 검게 입력되어 실제 YOLO `person` 양성 탐지는 확인하지 못했다. worker 실행과 이벤트 전송은 확인했지만 실제 사람 검출 성공을 의미하지는 않는다.
- 얼굴 등록 화면은 샘플 수집까지 완료됐지만, 임베딩 분석 companion 서비스가 없고 로컬 샘플 저장도 비활성화되어 학생과 얼굴 프로필의 영속 연결이 실패했다. 학생의 `face_registered` 값은 MongoDB에서 변경되지 않았고, 메모리 프로필은 FastAPI 재시작 후 사라졌다.
- 실행 중 새로 추가한 비디오 스트림은 ROI 서비스의 장기 캐시에 반영되지 않아 FastAPI를 재시작해야 ROI 화면에 나타났다.
- 학생 상태는 현재 `PRESENT`, `WRONG_SEAT`, `UNKNOWN`만 판정한다. 빈 탐지나 추적 소실을 시간 정책으로 해석해 `ABSENT`로 전환하는 기능은 아직 없다.
- 강의실 좌석 현황의 학생 상태 카드는 SSE로 갱신되지만, 상단 좌석 점유 요약은 별도의 좌석 geometry 상태를 사용한다. 두 지표의 의미와 갱신 기준을 일치시키거나 화면에서 명확히 구분해야 한다.
- SSE broadcaster는 FastAPI 프로세스 메모리에 있으므로 다중 프로세스 환경의 fan-out과 재연결 replay를 보장하지 않는다.

# 이어받을 때 알아야 할 것

## 다음 작업 우선순위

1. 얼굴 식별 모델을 `worker/inference/MODEL_INTEGRATION.md` 계약에 맞춰 연결한다. worker 이벤트에는 식별 성공 시 `student_id`, `identity_confidence`, 선택적으로 `face_bbox`만 추가한다.
2. 얼굴 등록 영속 경로를 완성한다. 임베딩 companion 서비스의 실행·헬스체크·설정을 갖추고, 샘플 저장 정책과 접근 제어를 확정한 뒤 임베딩 저장과 학생 `face_registered` 갱신을 하나의 검증 가능한 흐름으로 만든다.
3. 정상적으로 노출되는 웹캠에서 종단 간 수용 테스트를 다시 수행한다. 실제 사람 검출, 얼굴 식별, ROI 내부·외부 이동, 실시간 모니터링 표시, 대시보드 SSE 변화를 순서대로 확인한다.
4. 비디오 스트림 등록 API 또는 관리 UI를 제공하고, 실행 중 스트림 추가가 즉시 ROI 서비스에 반영되도록 캐시 무효화 또는 수명 관리를 수정한다.
5. `ABSENT` 정책을 정의한다. 수업 일정, 마지막 양성 탐지, grace period, tracker 소실을 어떤 규칙으로 해석할지 정하고 최종 상태 판정은 FastAPI가 담당하도록 유지한다.
6. 대시보드의 상단 좌석 점유 요약과 학생 상태 카드가 서로 다른 의미를 갖는 문제를 정리한다. 같은 상태를 보여줄지, 서로 다른 지표라면 명칭과 설명으로 분리할지 결정한다.
7. 다중 FastAPI 프로세스를 운영하려면 Redis 등 외부 pub/sub와 event replay 기준을 추가한다.

## 모델 담당자가 지켜야 할 경계

- 이름, 학번, 강의실, 좌석, 출결 상태를 모델에서 결정하거나 이벤트에 중복 적재하지 않는다.
- 모르는 얼굴은 미식별로 남기고 임의의 학생으로 매칭하지 않는다.
- 식별 성공 필드는 모두 함께 보내고, 재시도에는 같은 `event_id`를 사용한다.
- FastAPI 응답 201은 신규 저장, 200은 멱등 중복, 404는 알 수 없는 카메라, 409는 같은 이벤트 ID의 내용 충돌, 422는 계약 위반, 503은 저장소 장애로 처리한다.
- 현재 worker 재시도는 제한적이므로 장시간 장애 복구가 필요하면 별도 정책을 추가한다.

## 로컬 환경과 데이터 정리

- 테스트용 FastAPI, worker, 웹캠 게시 프로세스와 MediaMTX 컨테이너는 모두 중지된 상태다. Docker daemon과 외부 MongoDB는 종료하지 않았다.
- 중지된 MediaMTX 테스트 컨테이너는 남아 있어 필요하면 다시 시작하거나, 정확한 대상을 확인한 뒤 별도로 정리할 수 있다.
- MongoDB에는 웹캠 수용 테스트용 강의실·학생·좌석 지정·비디오 스트림·ROI 데이터가 남아 있다. 팀에서 재검증에 사용할지 결정한 뒤 정확한 식별자를 조회해 선택적으로 삭제해야 한다.
- 로컬 worker 설정과 YOLO 가중치는 Git에 포함하지 않는 ignored 파일이다. 비밀값이나 개인 데이터는 결과 문서에 기록하지 않았다.
- 기존 미추적 `.docker` 파일들은 이 작업 범위가 아니며 수정하거나 커밋하지 않았다.
