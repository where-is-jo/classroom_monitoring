# RPAs

업무 자동화(RPA) 프로젝트를 모아두는 디렉터리다.

`webapps`가 상시 실행되는 서비스라면, `RPAs`는 특정 업무를 대신 수행하는
독립 실행형 자동화 워크플로를 담는다.

## 이 디렉터리의 목적

- 반복 업무 자동화 스크립트를 프로젝트 단위로 관리한다.
- 각 자동화의 입력·출력·실패 처리 방식을 문서로 남긴다.
- 자동화가 다루는 데이터와 권한 범위를 명확히 한다.

## 디렉터리 구조

```text
RPAs/
├─ README.md              # 이 문서. 공통 규칙
├─ shared/                # 여러 RPA가 공유하는 문서와 자산
│  ├─ documentation/
│  └─ assets/
└─ examples/              # 새 RPA가 따라야 할 예시 구조 문서
```

## 프로젝트 생성 규칙

새 자동화는 반드시 `RPAs/<rpa-name>/` 아래에 독립 디렉터리로 만든다.
기존 RPA 디렉터리에 관련 없는 자동화를 끼워 넣지 않는다.

### 이름 규칙

- 소문자와 하이픈만 사용한다: `attendance-report`, `visitor-log-export`
- 업무 대상과 동작이 드러나는 이름을 쓴다. `rpa1`, `test-bot` 같은 이름은 쓰지 않는다.
- 디렉터리 이름과 문서 내 프로젝트 이름을 일치시킨다.

### 각 RPA 프로젝트에 필요한 것

최소 구성은 다음과 같다. 상세 구조는 [examples](./examples/README.md)를 참고한다.

- `README.md`: 목적, 트리거, 입력, 출력, 실행 방법, 실패 시 대응
- 자동화 실행 코드
- 설정 예시 파일(`.env.example` 등, 실제 값 제외)

## 자격 증명 취급

- 계정, 비밀번호, API 키, 토큰, 세션 쿠키를 저장소에 커밋하지 않는다.
- 자격 증명은 환경변수 또는 팀이 합의한 비밀 관리 수단으로 주입한다.
- 스크린샷·로그·샘플 데이터에 실제 개인정보나 자격 증명이 남지 않도록 확인한다.
- `.env.example`에는 변수 이름과 설명만 적는다.

## 입력과 출력 문서화

각 RPA는 다음을 README에 명시한다.

| 항목 | 설명 |
| --- | --- |
| 트리거 | 수동 실행 / 일정 / 이벤트 중 무엇인지 |
| 입력 | 파일, 조회 조건, 대상 시스템 |
| 출력 | 생성 파일, 전송 결과, 갱신된 레코드 |
| 성공 조건 | 무엇이 확인되면 성공인지 |
| 실패 조건 | 어떤 상황을 실패로 간주하는지 |

## 재시도와 중복 실행 처리

- 같은 입력으로 다시 실행해도 결과가 어긋나지 않도록 설계한다(재실행 가능성).
- 이미 처리한 대상을 다시 처리하지 않도록 처리 이력을 남긴다.
- 자동 재시도 대상(일시적 네트워크 오류)과 재시도하면 안 되는 대상(입력 오류, 권한 거부)을 구분한다.
- 되돌릴 수 없는 작업(메일 발송, 결재 승인, 삭제)은 자동 재시도하지 않는다.

## 로그와 장애 대응

- 실행 시작·종료, 처리 건수, 실패 원인을 로그로 남긴다.
- 로그에 자격 증명과 개인정보를 기록하지 않는다.
- 사람의 확인이 필요한 단계는 자동 진행하지 않고 중단 후 보고한다.
- 실패가 반복되면 원인을 해당 프로젝트 README의 문제 해결 절에 정리한다.
